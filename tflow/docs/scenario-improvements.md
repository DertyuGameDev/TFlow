# Завершённые сценарии участия

## Готовые локальные аккаунты

`python backend/manage.py seed_demo` создаёт (в DEBUG-окружении):

| Адрес | Роль | Назначение |
| --- | --- | --- |
| organizer@demo.example.test | Организатор | Создание и перенос флоу, просмотр посещений, выдача ключей |
| participant@demo.example.test | Участник | Регистрация, очередь, личная программа |
| helper@demo.example.test | Участник | Доверенный сканер/ведущий по ключу; уже занимает одно место в демо-лекции |

Пароль всех трёх: `Demo-flow-2026!`. Это только тестовые аккаунты; команда запрещена в production, существующие пароли и роли не перезаписывает.
Демо «Конференция без накладок» содержит две аудитории, пересекающиеся лекции и более поздний практикум. В «Лекции с очередью» одно место занято помощником. Отдельное онлайн-событие содержит два параллельных эфира. Повторный seed не добавляет записи заново, не отменяет ручные изменения и не дублирует данные.

## Правила регистрации и очереди

Билет даёт доступ на мероприятие. Выбранные флоу показываются отдельно с количеством; кнопка ведёт к их списку. Для закрытых флоу нужна отдельная запись, открытые доступны по билету; добавление открытого флоу в личное расписание не резервирует место. Отмена билета отменяет записи и очереди всего события, о чём заранее сообщает диалог.
При освобождении места очередь записывает первого подходящего человека автоматически. Занятое время приостанавливает получение места, но не удаляет позицию: следующий подходящий участник может получить место раньше. После отмены конфликтующей записи очередь проверяется снова. Интерфейс показывает состояние приостановки, название конфликта и правила продвижения.

## Посещаемость

В QR-сканере выберите «Вход на мероприятие» либо «Посещение флоу: …». Вход и посещения хранятся отдельно. Для флоу требуется его регистрация; для открытого достаточно билета. Успешный скан активности также подтверждает вход на мероприятие, сохраняя прежнюю отметку, если она уже есть. Повтор одного и того же посещения запрещён, посещение другого флоу разрешено.
QR-ключ доверенного лица ограничен своим мероприятием и позволяет выбирать только его флоу; контакты и анкета в ответ не передаются. Роль аккаунта не меняется. Ключ ведущего остаётся привязанным к одному онлайн-флоу. Вебинар засчитывает посещение после подтверждения подключения медиасервером, а не после выдачи токена. В кабинете видны число посещений флоу и посещённые активности каждого участника.

## Конфликты и уведомления

При конфликте переноса сервер сообщает пересекающиеся активности, количество затронутых участников и до трёх подходящих вариантов времени/аудитории. Чужие анкеты и названия событий других организаторов не раскрываются. Предложения не бронируются: при сохранении проверка выполняется заново. Если подходящих вариантов нет, организатор получает явное объяснение.
В уведомлениях о переносе указаны прежние и новые время/аудитория. Уведомление флоу открывает его карточку и ставит на неё фокус. Удалённая активность оставляет уведомление с переходом на событие.
За 30 минут до начала выбранного флоу создаётся напоминание. Повторный запуск не дублирует его, отменённая запись и черновик не получают напоминаний; изменение времени позволяет отправить новое напоминание. Сообщение и отметка отправки сохраняются одной транзакцией.

В dev обработчик запускается вместе с `npm run dev`, SMTP для сообщений на сайте не нужен. Разовый запуск: `python backend/manage.py send_activity_reminders`. Для сервера — systemd timer из `monitoring/install.py`.

## Производительность

`python scripts/benchmark-registration.py` создаёт временную SQLite-базу, применяет миграции и удаляет её после проверки; основная база не используется. Проверяются 200 HTTP-запросов, 20 потоков, 40 активностей. Текущий локальный замер:

| Сценарий | Итог | Время | p95 ответа |
| --- | --- | --- | --- |
| 200 попыток на 5 мест | Ровно 5 регистраций, без 5xx | 2,61 с | 1,05 с |
| 200 записей на 40 флоу | Все 200 регистраций, без 5xx | 6,03 с | 2,57 с |

Это замер SQLite на текущей машине, а не гарантия production-SLA. Одна общая блокировка пока сохранена: она защищает в том числе межсобытийные конфликты личного расписания. Разделение только по event_id нарушило бы эту гарантию. В Prometheus/Grafana добавлены ожидание и длительность удержания блокировки; перед дальнейшим дроблением нужен такой же нагрузочный прогон на PostgreSQL рабочего сервера.
