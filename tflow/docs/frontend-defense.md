## 1. Что мы делаем и в чём роль фронтенда

ТФлоу объединяет поиск мероприятий, запись, персональную программу, посещение и онлайн-эфиры. Участник видит связанные действия в одном интерфейсе: находит событие, записывается, выбирает активности, получает расписание и использует личный QR. Организатор создаёт событие, распределяет программу по аудиториям, управляет участниками и открывает студию эфира.

Главная особенность интерфейса — работа не только с карточкой мероприятия, но и с его внутренней программой. Одновременно могут идти несколько активностей в разных аудиториях, включая онлайн. Пользователю нужно видеть время, длительность, доступность мест и пересечения.

**Рассказ на минуту:**

> Фронтенд ТФлоу написан на React и TypeScript. Он связывает каталог, запись, календарь, программу мероприятия, QR-вход и эфиры. Мы вынесли расчёт времени и размещения активностей в отдельные функции, чтобы проверять сложную логику независимо от отображения. React управляет состоянием экранов, а Django проверяет права и сохраняет данные. Интерфейс адаптируется под телефон, поддерживает две темы, клавиатурную навигацию и понятные состояния загрузки и ошибок. Для видео предусмотрены два транспорта: LiveKit для WebRTC и HTTPS/HLS для серверов, где нельзя открыть медиапорты. Их возможности и ограничения различаются.

## 2. Технологии: что используется и зачем

Источники версий: [package.json](../package.json), [package-lock.json](../package-lock.json), [tsconfig.json](../tsconfig.json).

- **React и React DOM 19.2.6.** Компоненты описывают повторяемые части интерфейса, состояние определяет отображение. Подход подходит для форм, фильтров, диалогов, расписания и медиастудии. React DOM связывает дерево компонентов с DOM браузера. Сам по себе React не является сервером или базой данных.
- **TypeScript 5.9.3.** Проверяет типы на этапе разработки. Например, отличает мероприятие `FlowEvent` от активности `Activity`, фиксирует допустимые роли и свойства компонентов. Включён `strict`. Типы не проверяют автоматически JSON, пришедший по сети, и не заменяют серверную валидацию.
- **Vite 8.1.6 и плагин React 6.0.2.** Запускают сервер разработки, обновляют интерфейс при изменениях и собирают production-ресурсы. Во время разработки Vite проксирует API к Django. После сборки браузеру нужны готовые JS/CSS, а не Vite.
- **CSS и Tailwind CSS 4.2.1.** Tailwind подключён через CSS, но большая часть текущего интерфейса оформлена собственными классами и CSS-переменными. Правильно говорить «собственный CSS с подключённым Tailwind», а не «вся вёрстка на utility-классах».
- **Lucide React.** Единый набор SVG-иконок: календарь, камера, поиск и другие действия. Размер и цвет согласуются с компонентами; декоративные иконки не должны дублировать текст для скринридера.
- **Шрифт Golos.** Локальный файл в `public/fonts`, используется для русскоязычного интерфейса. Загрузка шрифта не зависит от стороннего сервиса шрифтов; браузер всё равно должен получить файл с нашего сайта.
- **Fetch API.** Встроенные HTTP-запросы браузера. Для текущего API не потребовался Axios: есть общая функция отправки, обработка ошибок и CSRF. У видео есть отдельный клиент с таймаутами.
- **ZXing: `@zxing/browser` и `@zxing/library`.** Распознавание QR с камеры и изображения. Библиотека декодирует QR; право входа проверяет сервер.
- **`livekit-client`.** Подключение к видеосерверу LiveKit, публикация и получение медиатреков в WebRTC-режиме.
- **`hls.js` 1.7.4.** Воспроизведение HLS в браузерах с подходящей поддержкой Media Source Extensions. При наличии встроенного HLS используется браузерный проигрыватель.
- **Vitest, Testing Library, user-event, jest-dom и jsdom.** Проверка вычислений и поведения компонентов: что видит пользователь, что происходит при клике, вводе, ошибке или ответе API. jsdom моделирует DOM, но не физическую камеру и не реальную мобильную вёрстку.
- **Node.js от 22.13.0.** Нужен инструментам разработки, сборке и тестовым скриптам. Для раздачи собранного интерфейса через Django отдельный Node-сервер не требуется.

В текущем приложении нет Redux, React Router, Next.js и Axios. Название папки `app` и встречающаяся директива `"use client"` не превращают проект в Next.js. Нет отдельного Redux-store или автоматического SSR.

## 3. Архитектура и карта проекта

```text
Браузер
  index.html → src/main.tsx → TFlow
                                ├─ экраны и компоненты app/ui
                                ├─ расчёты и типы lib
                                └─ fetch /api/… → Django → база данных

Видео, если выбран LiveKit:
  Django выдаёт разрешение → браузер подключается к LiveKit

Видео, если выбран HTTPS-режим:
  браузер ведущего → HTTP-фрагменты → Django + FFmpeg worker
  браузер зрителя  ← HLS-плейлист и сегменты ← сервер

Вход и регистрация:
  Django HTML-формы + public/auth.js + общие стили/тема/поиск интересов
```

### Основные слои

- [src/main.tsx](../src/main.tsx) — точка входа React, запрос текущего пользователя, начальные состояния подключения.
- [app/tflow.tsx](../app/tflow.tsx) — маршруты, общие данные, запросы, диалоги, действия пользователя и сборка основных экранов.
- [app/ui](../app/ui) — компоненты: календарь, формы, выбор категории, карточки, управление событием, сканер, студия.
- [lib/types.ts](../lib/types.ts) — договорённости о форме данных и общий каталог категорий.
- [lib](../lib) — вычисления времени, пересечений, размещения программы, медиавспомогательные функции.
- [app/globals.css](../app/globals.css), [app/responsive.css](../app/responsive.css), [app/flow.css](../app/flow.css) и стили отдельных компонентов — оформление.
- [public](../public) — доступные браузеру статические файлы: тема, шрифты, SVG, скрипты страниц авторизации.
- [backend/flow](../backend/flow) — API и бизнес-правила. Это серверная часть, которая задаёт ограничения для интерфейса.

**Почему отделять расчёты от JSX:** алгоритм размещения можно проверить обычными объектами времени без запуска браузера. Один расчёт используется разными представлениями, а компоненты занимаются отображением и взаимодействием.

**Граница нынешней архитектуры:** корневой `TFlow` остаётся большим компонентом с несколькими обязанностями. Это рабочее решение, но выделение API-слоя, маршрутов и загрузки данных в отдельные модули упростило бы сопровождение.

## 4. Что происходит при открытии сайта

1. Браузер загружает [index.html](../index.html). Скрипт темы запускается до React, чтобы сразу выставить светлое или тёмное оформление.
2. `src/main.tsx` выполняет `GET /api/auth/me` с cookie текущего домена.
3. Пока идёт запрос, показывается состояние подключения. Если сервер недоступен — сообщение и повторная попытка, а не пустая страница.
4. Ответ определяет пользователя и роль; для гостя пользователь равен `null`.
5. `TFlow` читает маршрут из `location.hash` и загружает `/api/bootstrap`.
6. Для страницы конкретного мероприятия запрашиваются его подробности. Список участников загружается отдельно для нужных организаторских экранов.
7. React отображает данные. После успешного изменения приложение обновляет данные с сервера.

Начальный запрос использует `AbortController`: при размонтировании его можно отменить. В других загрузчиках применяются номера запросов, чтобы устаревший ответ не заменил более свежие данные.

### Маршрутизация

Собственный небольшой маршрутизатор находится в `routeFromHash` и `go` внутри `app/tflow.tsx`. Примеры:

- `/#events` — каталог;
- `/#event/<eventId>` — мероприятие;
- `/#calendar` — личный календарь;
- `/#profile` — профиль;
- `/#clubs` — клубы;
- `/#organizer` — кабинет организатора;
- `/#manage/<eventId>` — управление;
- `/#scan/<eventId>` — проверка QR для события;
- `/#webinar/<eventId>/<activityId>` — эфир конкретной активности; без последней части — общий эфир события.

Изменение hash обрабатывается через `hashchange`; кнопки браузера «назад» и «вперёд» меняют его обычным способом. Неизвестный раздел ведёт к начальному экрану соответствующей роли.

**Почему это удобно для проекта:** ссылкой можно поделиться без настройки серверного маршрута для каждого экрана; hash не отправляется серверу как путь HTTP-запроса. **Цена:** маршруты и проверка их параметров поддерживаются вручную; полноценного SSR и метаданных для каждой карточки такая схема сама не даёт.

### Какие данные получает фронтенд

В `Bootstrap` входят каталог событий, билеты, выбранные активности, очередь, клубы, уведомления, счётчик непрочитанного и профиль. `EventDetail` содержит одно мероприятие, аудитории и его активности.

- `FlowEvent` — рамки всего мероприятия, владелец, формат, вместимость, публикация и счётчики.
- `Room` — аудитория внутри мероприятия; может быть онлайн.
- `Activity` — конкретный пункт программы: время, аудитория, спикер, места и состояние записи.
- `Profile` — контактные и дополнительные данные пользователя, роль и личный пропуск.
- `AttendanceRow` — данные регистрации и отметка входа для организатора.

Мероприятие и активность — разные сущности. Запись на мероприятие и добавление активности в персональную программу — разные операции.

## 5. Состояние React, запросы и ошибки

### Где хранится состояние

- `useState` — то, что влияет на отображение: данные, фильтры, открытый диалог, ошибки, занятость кнопки, выбранное событие.
- `useRef` — изменяемые значения, обновление которых само по себе не требует рендера: номер запроса, экземпляр видеокомнаты, медиатрек, блокировка повторного сканирования.
- `useEffect` — связь с внешним миром: запросы, таймеры, обработчики событий, подключение медиа и очистка ресурсов.
- `useCallback` — стабильная ссылка на функции, используемые в зависимостях и передаваемые компонентам.
- `useMemo` — вычисленные структуры там, где это используется, например раскладка флоу. Это оптимизация, а не место для побочных эффектов.

Общие данные поднимаются в `TFlow`, локальные остаются у формы или компонента. Например, текст поиска внутри выбора категории не должен становиться глобальным состоянием всего приложения.

### Как React обновляет страницу

Компонент — функция, которая возвращает описание интерфейса через JSX. При изменении состояния React снова вызывает нужные компоненты, сравнивает новое описание с предыдущим и применяет изменения к DOM. Повторный вызов компонента не означает полную перезагрузку сайта или обязательную замену всех DOM-элементов.

В списках стабильный `key`, обычно ID сущности, помогает связать элемент со старым экземпляром. Индекс массива неудобен для списка, в котором элементы меняются местами: состояние строки может оказаться связано с другой записью.

Состояние обновляется через setter, а не прямым изменением объекта. Если новое значение зависит от предыдущего, используется функциональная запись вроде `setSelected(previous => [...previous, category])`. Она работает с актуальным предыдущим значением. Мемоизация не заменяет эту корректность и не должна добавляться ко всем функциям без причины.

### Общий HTTP-клиент

Функция `send` в `app/tflow.tsx` добавляет `/api/`, передаёт cookie через `credentials: "same-origin"`, сериализует обычное тело в JSON и добавляет `X-CSRFToken` для изменяющих запросов. Если тело — `FormData`, `Content-Type` вручную не устанавливается: браузер добавляет границу multipart сам.

При `401` интерфейс отправляет на вход с адресом возврата. Ошибочный ответ становится [ApiError](../lib/api-error.ts) с сообщением, кодом, ошибками полей и перечнем недостающих данных профиля.

В UI различаются:

- начальная загрузка;
- пустой каталог или отсутствие результатов фильтра;
- ошибка загрузки;
- ошибка отдельного поля;
- выполняющееся действие;
- успешное действие и уведомление.

Это важно: отсутствие событий не равно недоступности сервера. Показывать одинаковую пустую страницу в этих случаях было бы ошибкой.

### Обновление и гонки запросов

После изменения выполняется повторное чтение данных. Это уменьшает риск расхождения счётчиков, очереди и мест с сервером. Большинство таких действий не является полноценным optimistic update: UI ожидает результат, затем обновляет состояние.

Есть polling: для участника на экранах профиля/события интервал составляет 5 секунд, в остальных случаях — 15 секунд; фоновая загрузка выполняется при видимом документе. Возврат фокуса обновляет данные. Видеокомпоненты имеют собственные интервалы.

`loadSequence` и `detailSequence` защищают от гонки: если пользователь быстро открыл событие A, затем B, поздний ответ A не должен перезаписать B. Это защита состояния интерфейса, а не отмена выполнения запроса на сервере.

`pending`, `busy` и локальные блокировки уменьшают повторные клики. Они не гарантируют атомарность записи: два разных браузера всё равно могут одновременно отправить запрос. Окончательные проверки выполняет Django.

## 6. Пользовательские сценарии

### Гость и авторизация

Гость может знакомиться с публичными данными; действия, требующие аккаунта, ведут на вход или регистрацию. Адрес возврата позволяет продолжить с нужного мероприятия.

Вход, регистрация и выход обслуживаются Django. Это обычные HTML-формы с дополнительным JavaScript, а основная часть приложения — React SPA. Общие статические файлы поддерживают согласованную тему и оформление между ними.

В регистрации есть выбор роли «Участвовать» / «Организовывать». Роль — серверное правило аккаунта, а не временный фильтр UI. Её нельзя считать изменённой от переключения переменной в браузере. Источники: [шаблон выбора роли](../backend/flow/templates/widgets/registration_role.html), [auth.js](../public/auth.js).

### Участник: от каталога до посещения

1. Находит событие поиском и фильтрами.
2. Открывает подробности и программу.
3. Записывается на мероприятие. Если организатор запросил дополнительные данные, заполняет недостающее.
4. При отсутствии мест использует очередь, когда это допускает сервер.
5. Добавляет доступные активности в персональную программу; видит предупреждения о пересечениях.
6. Открывает календарь и личный QR в профиле либо входит в доступный онлайн-эфир.
7. После серверного подтверждения входа видит отметку посещения.

Каталог различает все, активные и завершённые мероприятия. Дополнительные признаки «идут сейчас» и подтверждённое посещение находятся в фильтрах. Завершённые события визуально приглушены; посещение отмечается отдельно. Формулировка статуса не должна зависеть от пола пользователя.

Активность может быть недоступна для новой записи, если уже началась, места закончились или она пересекается с выбранной программой. Уже записанному участнику должна оставаться доступна отмена. Логика: [activityAvailability](../lib/activities.ts).

### Организатор

Кабинет показывает свои будущие события и архив. Организатор создаёт черновик, задаёт общие рамки времени и формат, добавляет аудитории и активности, публикует мероприятие, работает со списком участников, QR и студией. Действия переноса и удаления имеют отдельные сценарии, а опасное действие требует подтверждения.

Принадлежность события проверяется в интерфейсе для удобства, но право изменения проверяется сервером. Скрыть кнопку недостаточно для защиты API.

Основные компоненты: [QuickEventForm](../app/ui/quick-event-form.tsx), [OrganizerManage](../app/ui/organizer-manage.tsx), [EventRemovalDialog](../app/ui/event-removal-dialog.tsx), [OrganizerTutorial](../app/ui/organizer-tutorial.tsx).

### Клубы и уведомления

[Clubs](../app/ui/clubs.tsx) объединяет поиск клубов, категорию, создание, вступление и подписку на новые события. Членство и настройка уведомлений — разные состояния.

[NotificationCenter](../app/ui/notification-center.tsx) умеет показывать все/непрочитанные, отмечать прочтение и загружать следующие страницы по курсору. При объединении страниц записи дедуплицируются по ID. Это отличается от бесконечного получения всего архива при каждом запросе.

Внутренние уведомления получает фронтенд через API. Отправка электронной почты выполняется сервером и его обработчиком; браузер не подключается к SMTP и не хранит пароль почты.

## 7. Флоу: как время становится визуальной программой

Источники: [FlowSchedule](../app/ui/flow-schedule.tsx), [flow-layout.ts](../lib/flow-layout.ts), [flow-markers.ts](../lib/flow-markers.ts), [readable-flow.ts](../lib/readable-flow.ts), [flow-navigation.ts](../lib/flow-navigation.ts).

### Базовая идея

Вертикальная координата соответствует времени, высота — длительности, параллельные активности располагаются рядом. В базовой линейной проекции:

```text
Y = начало_полотна + (время − начало_интервала) / 60 000 × пиксели_на_минуту
Высота = (конец − начало) / 60 000 × пиксели_на_минуту
```

Метки и короткие карточки дополнительно обрабатываются для читаемости. Поэтому не нужно обещать, что каждый видимый пиксель во всех режимах строго равен одной и той же доле минуты: есть слой визуальной адаптации, который не меняет исходные времена.

Флоу получает границы родительского мероприятия и показывает весь интервал от начала до конца, включая пустое время. Без этих границ визуализация могла бы ограничиться только первой и последней активностями. Поддерживается непрерывный интервал через полночь; время и подписи остаются в МСК.

### Размещение пересечений

1. Копия массива сортируется по началу, окончанию и ID.
2. Собираются связанные группы пересекающихся интервалов.
3. Для каждой активности выбирается первая освободившаяся колонка; если её нет — создаётся новая.
4. Ширина зависит от числа параллельных колонок. Если справа нет пересекающегося блока, элемент может занимать дополнительное свободное место.

Пример: A идёт 10:00–11:00, B — 10:30–11:30, C — 11:00–12:00. A и B располагаются рядом. C может использовать освободившуюся колонку A, но продолжает идти параллельно B.

Условие пересечения:

```ts
a.starts_at < b.ends_at && a.ends_at > b.starts_at
```

Окончание одного пункта в 11:00 и начало другого ровно в 11:00 не создают пересечение. Удобная модель — полуоткрытые интервалы `[начало, конец)`.

Сортировка занимает `O(n log n)`, но вся реализация не сводится к этой сложности: поиск колонок и расширение блоков дополнительно перебирают элементы. На плотных группах есть квадратичные проходы. Для текущих размеров программ это разумное решение; производительность на тысячах одновременных пунктов не доказана.

### Цвет, текущее время и масштаб

- Цвет вычисляется из стабильного ID активности и общей палитры `PROGRAM_COLORS`. Перестановка массива не должна случайно перекрашивать карточки. Палитра конечна: уникальный цвет для каждого пункта не гарантируется.
- Красная линия и подпись `чч:мм` показывают текущее время. Близкие подписи шкалы учитываются, чтобы не накладываться на индикатор.
- `useFlowClock` планирует обновление к следующей минуте или ближайшей границе активности и реагирует на возвращение фокуса/видимости. Для этого не нужен рендер всей программы 60 раз в секунду.
- Масштаб выбирается из нескольких значений пикселей на минуту. Преобразования времени и координаты помогают сохранить контекст при увеличении.
- На узких экранах сложная параллельная программа может прокручиваться внутри своего полотна. Это лучше, чем сжимать все колонки до нечитаемых слов или растягивать весь документ по горизонтали.

Нужно различать **прокрутку внутри визуализации** и случайное горизонтальное переполнение всей страницы.

## 8. Редактирование программы

Источники: [ProgramTimeline](../app/ui/program-timeline.tsx), [use-timeline-editor](../app/ui/use-timeline-editor.ts), [ProgramGraphEditor](../app/ui/program-graph-editor.tsx), [program-editing.ts](../lib/program-editing.ts), [ProgramSwap](../app/ui/program-swap.tsx).

Есть визуальное представление по времени и аудиториям, а также форма с явными значениями времени. Визуальное управление не должно быть единственным способом редактирования: точные значения проще задать полями, особенно на телефоне.

Чистые функции переводят координату указателя во время, округляют к шагу, ограничивают перенос рамками мероприятия и изменяют нужную границу активности. При обычном перемещении длительность сохраняется. При изменении начала/конца проверяется минимальный интервал и границы.

Предпросмотр изменения отличается от сохранения. Пока действие не подтверждено, вычисленный диапазон используется в UI; окончательное решение принимает API. Клиентская проверка конфликта аудитории позволяет раньше объяснить проблему, но не заменяет серверную проверку актуального расписания.

### Обмен пунктов местами

Это не просто обмен двух подписей. Сценарий `ProgramSwap`:

1. Выбрать другой пункт.
2. Отправить `POST /api/activities/<id>/swap` с `preview: true` и `expected_event_updated_at`.
3. Получить список изменений «было → будет», включая затронутые промежуточные пункты.
4. Подтвердить обмен отдельным запросом с ожидаемой версией.
5. После успеха обновить данные; при конфликте показать ошибку и не оставлять старый предпросмотр как будто он действителен.

`updated_at` используется для обнаружения устаревшей версии. Это optimistic concurrency — проверка версии при записи. Не путать с optimistic UI, когда интерфейс заранее изображает успех до ответа сервера.

Транзакционность, права, вместимость и конфликты записей — ответственность серверных сервисов. Фронтенд показывает причины отказа и не пытается обходить их.

## 9. Календарь и работа со временем

Источники: [Calendar](../app/ui/calendar.tsx), [calendar.ts](../lib/calendar.ts), [time.ts](../lib/time.ts), [серверный экспорт](../backend/flow/calendar.py).

Персональный календарь собирает билеты на события, выбранные активности и собственные мероприятия организатора. Источники различаются, а повторное представление собственного события через билет исключается.

### Главное правило времени

В API используются временные отметки в миллисекундах. Отображение — в `Europe/Moscow`. HTML-поле `datetime-local` не содержит часового пояса, поэтому его значение явно преобразуется как московское время, а не как местное время компьютера.

- `dateLabel` и `timeLabel` используют `Intl.DateTimeFormat` с московским часовым поясом.
- `localInput` готовит московские дату и время для поля.
- `fromLocalInput` добавляет `+03:00`, когда превращает значение поля во временную отметку.
- Календарные дни также рассчитываются в МСК.

Это сознательное правило текущего продукта, а не универсальная поддержка любого часового пояса. При расширении на другие зоны понадобится явная модель зоны мероприятия и более общая работа с переходами времени.

### Месяц, день и интервалы

Месячная сетка строится по полным неделям с понедельника. Переключение месяцев учитывает длину месяца, например переход с 31 января. Проверка даты отсекает невозможные даты.

В дневном представлении события через полночь обрезаются по границам выбранного дня и отмечаются как продолжающиеся. Конец ровно в полночь не создаёт лишнее событие следующего дня. Пересекающиеся элементы располагаются в колонках; для коротких записей резервируется читаемое место без изменения реальной длительности.

### Экспорт `.ics`

Сервер отдаёт файл для одного события через `/api/events/<id>/calendar` и для персональной программы через `/api/schedule/calendar`. Интерфейс предлагает его скачать/открыть во внешнем календаре.

Это экспорт снимка данных. Не нужно обещать двустороннюю или автоматическую синхронизацию с Google Calendar: OAuth-интеграции и подписки календаря сам факт скачивания `.ics` не создаёт.

## 10. QR-пропуск и сканер

Источник: [QRScanner](../app/ui/qr-scanner.tsx), проверки [qr-scanner.test.tsx](../tests/ui/qr-scanner.test.tsx), серверные правила [services.py](../backend/flow/services.py).

QR в профиле — личный пропуск участника. Внутри используется токен, а не признак «человека уже пропустили». При проверке обязательно задано мероприятие, на которое организатор отмечает вход.

### Сценарий организатора

1. Выбрать своё событие; если оно единственное, оно может быть выбрано автоматически. Контекст выбранного мероприятия остаётся видимым.
2. Нажать включение камеры или загрузку QR. Разрешение камеры не запрашивается при случайном открытии страницы.
3. ZXing распознаёт код; камера по возможности выбирается задняя.
4. Фронтенд отправляет `POST /api/events/<id>/check-in` с распознанным `qr`.
5. Сервер проверяет организатора, регистрацию участника и предыдущий вход.
6. UI показывает результат и данные участника. Повторный код не должен увеличивать число вошедших.

Есть загрузка изображения и ручной ввод содержимого/ссылки как альтернативные пути. Для чистых QR-изображений предусмотрен дополнительный способ декодирования через библиотеку.

### Технические детали, которые могут спросить

- `getUserMedia` требует разрешения и защищённого контекста: HTTPS либо допустимого локального адреса. Обычный HTTP по IP в локальной сети не равен `localhost` телефона.
- ZXing загружается динамически, чтобы тяжёлое распознавание не требовалось каждому посетителю каталога сразу.
- Блокировка обработки уменьшает повторные запросы, когда камера видит один QR много кадров подряд.
- При уходе/остановке освобождаются камера и служебные ресурсы; поздний результат запуска не должен заново включить уже закрытый сканер.
- Изображение декодируется клиентской библиотекой; для отметки входа отправляется значение QR. Это не доказывает личность по фотографии.
- QR — чувствительный пропуск. Копирование скриншота само по себе не предотвращается оформлением UI. Нельзя называть его криптографическим подтверждением личности предъявителя.

## 11. Вебинары: два разных транспорта

Источники: [Webinar](../app/ui/webinar.tsx), [HttpWebinar](../app/ui/http-webinar.tsx), [http-broadcast.ts](../lib/http-broadcast.ts), [webinars.ts](../lib/webinars.ts), [описание серверного режима](webinar-updates.md).

**Ключевой факт для защиты:** общий интерфейс поддерживает два пути передачи медиа. Выбор определяется серверной конфигурацией и ответом статуса. Это не доказательство, что после любой сетевой ошибки браузер автоматически и бесшовно заменит LiveKit на HLS.

### 11.1. LiveKit / WebRTC

1. Браузер запрашивает статус и разрешение для эфира события или активности.
2. Django проверяет права и возвращает адрес видеосервера, токен, роль ведущего и сессию.
3. `livekit-client` подключает браузер к комнате.
4. Медиа передаются через инфраструктуру LiveKit, а React отображает локальные/удалённые треки и состояние подключения.

LiveKit использует SFU: сервер принимает потоки и пересылает подписчикам. Не нужно описывать это как полносвязную P2P-сетку, где каждый браузер отправляет отдельное видео каждому зрителю.

У публикации камеры, микрофона и экрана есть разрешения. Право публикации задаётся сервером, а не только тем, показали ли кнопку. Студия и экран просмотра могут различаться.

Для публичного HTTPS-сайта нужен корректный публичный защищённый адрес видеосервера. `ws://localhost:…` в настройке означает компьютер посетителя, а не удалённую VM. Клиент специально проверяет такие ошибки конфигурации и смешение HTTPS/незащищённого WebSocket.

Медиадоступность WebRTC зависит от сети, TLS и настройки видеосервера. Тот факт, что обычная страница открылась на 443, не гарантирует прохождение медиа по всем нужным маршрутам.

### 11.2. HTTPS-трансляция / HLS

Этот режим позволяет передавать эфир через обычные HTTP-запросы приложения, когда нет возможности открыть отдельные медиапорты VM.

1. Ведущий разрешает камеру/микрофон или демонстрацию экрана.
2. `BroadcastCapture` собирает итоговое видео на canvas и звук через Web Audio. Отрисовка видео идёт с частотой около 15 кадров в секунду.
3. `MediaRecorder` кодирует доступным браузеру форматом; поддержка MIME проверяется через `isTypeSupported`.
4. `BroadcastUpload` последовательно отправляет фрагменты с номером, сессией и разрешением публикации. Есть таймаут, ограниченная очередь и повторы для временных ошибок.
5. Постоянный серверный обработчик FFmpeg преобразует поток в HLS с H.264/AAC.
6. Зритель получает плейлист и сегменты: через `hls.js` либо встроенный HLS.

Это поток «ведущий → зрители» с буферизацией и задержкой. Его нельзя представлять как равноценную замену интерактивной многопользовательской видеоконференции WebRTC. Точную задержку без замера на конкретной сети обещать нельзя.

HTTP-режиму нужны постоянный процесс FFmpeg, общий каталог данных и корректная работа reverse proxy. В текущей реализации он отключён на Vercel: обычная serverless-функция не заменяет постоянный процесс кодирования. На VM такой режим можно обслуживать отдельной службой.

По умолчанию сервер ограничивает число одновременных HTTP-эфиров двумя, а входной фрагмент — 2 МиБ. Число потоков задаётся серверной настройкой. Это ограничения реализации, а не результаты нагрузочного тестирования.

### 11.3. Чат, параллельные эфиры и доступ лектора

У онлайн-активностей отдельные студии и адреса. Разные активности не должны случайно объединять видео, звук и чат в один эфир. В UI есть выбор онлайн-флоу и общий эфир мероприятия.

В HTTPS-компоненте состояние обновляется примерно каждые 2,5 секунды, чат — каждые 2 секунды. У LiveKit-экрана статус запрашивается каждые 5 секунд. Это polling, а не WebSocket-чат с гарантированно мгновенной доставкой.

Автор серверного сообщения определяется по аккаунту на сервере: используется часть почты до `@`. Произвольный автор, присланный клиентом, не должен считаться доверенным. Из подписи убран домен, но оставшийся логин почты тоже может быть персональными данными.

[PresenterAccess](../app/ui/presenter-access.tsx) открывает ограниченную студию по персональной ссылке. Пользователю нужен вход в аккаунт; сервер разрешает только эфир указанной активности. Это не выдача полной роли организатора. Ссылку можно отозвать/обновить. Значение приглашения сохраняется в `sessionStorage`, а затем убирается из адресной строки через `history.replaceState`. Служебные данные восстановления HTTP-эфира также могут храниться в `sessionStorage`; это не хранилище пароля аккаунта.

### 11.4. Браузерные ограничения и очистка

- Доступ к устройствам запрашивается действием пользователя.
- Воспроизведение со звуком может требовать клика из-за autoplay-политики.
- Показ экрана запускается в обработчике пользовательского действия, иначе браузер может отказать. Разрешение iframe на screen capture — отдельное условие.
- Отмена выбора устройства или экрана — штатная ситуация, для неё показывается понятная ошибка.
- При выходе останавливаются собственные треки, таймеры и загрузки; HLS-плеер уничтожается. Иначе можно оставить занятую камеру или фоновую передачу после закрытия экрана.
- После обновления студии устройства требуют повторного разрешённого подключения; сохранённая сессия не даёт возможности тайно восстановить камеру.
- Интерфейс реконнекта помогает при временных сбоях, но не исправляет закрытый порт, неверный TLS или отсутствие серверного worker.

## 12. Формы, профиль, категории и интересы

### Формы и профиль

Источники: [forms.tsx](../app/ui/forms.tsx), [profile-data.tsx](../app/ui/profile-data.tsx), [profile-fields.ts](../lib/profile-fields.ts), [CityPicker](../app/ui/city-picker.tsx).

Используются нативные формы и поля, `FormData`, контролируемые значения там, где нужно синхронно отражать ввод, и общие компоненты ошибок/кнопок сохранения.

В редакторе профиля обязательна учётная почта: она отмечена красной звёздочкой и показана только для чтения. PATCH профиля не отправляет её на изменение. Имя, фамилия и дополнительные поля можно оставить пустыми. Необязательность не отменяет проверку формата, если значение введено.

Это правило редактора профиля. Не нужно переносить его на создание аккаунта: регистрация также требует предусмотренные формой учётные данные. Кроме того, конкретный организатор может потребовать дополнительные данные при записи на своё мероприятие.

Если API возвращает `PROFILE_INCOMPLETE` и `missing_fields`, `CompleteRegistrationForm` показывает недостающие поля и позволяет продолжить. Требования задаёт сервер; клиент не должен сам объявлять профиль полным. Данные регистрации сохраняются сервером как данные для организатора; изменение профиля не следует автоматически считать изменением всех прошлых регистраций.

Город вводится через подсказки. Аватар передаётся как файл через multipart, а не как строка URL из произвольного внешнего источника. Ограничения файла нужно проверять и на сервере.

### Выбор одной категории

Источники: [CategorySelect](../app/ui/category-select.tsx), [category-select.css](../app/category-select.css).

Для фильтра/формы используется компактное поле поиска с ограниченным по высоте выпадающим списком. Начальная выдача короткая; ввод позволяет найти категорию во всём каталоге. В фильтре есть вариант «все категории», в обязательном поле формы нужна конкретная категория.

Меню позиционируется поверх содержимого и учитывает доступное место, включая диалоги и мобильный viewport. Оно не должно растягивать строку фильтров на высоту всего каталога. Пользователь может прокручивать результаты, выбирать касанием и работать клавишами стрелок, Enter и Escape.

Текст запроса и сохранённая категория — разные состояния. Просто написать слово недостаточно для выбора: нужно выбрать подсказку. Escape/уход из поля не должны незаметно заменять предыдущую категорию случайным текстом. Скрытый нативный `select` сохраняет отправку выбранного значения через `FormData` и проверку обязательности.

### Несколько интересов

[InterestPicker](../app/ui/interest-picker.tsx) — другой компонент: поиск, несколько выбранных категорий и удаляемые теги. Подсказки появляются при вводе; уже выбранные пункты исключаются из предложений. В регистрации аналогичное поведение реализовано без React в [registration-interests.js](../public/registration-interests.js).

Справочник один: [interest_categories.json](../backend/flow/interest_categories.json). Поиск нормализует регистр и `ё/е`, учитывает названия групп и предусмотренные синонимы вроде `ИИ`/`AI`. Общая функция — [interest-search.js](../public/interest-search.js).

Такой поиск детерминированный, по локальному справочнику. Это не нейросетевой поиск и не создание новых категорий по произвольному тексту. Для небольшого каталога серверный запрос на каждую букву не нужен.

## 13. Визуальный стиль, телефон и доступность

### Оформление и темы

Общая система: Golos, жёлтый акцент для основных действий, нейтральные поверхности, единая библиотека иконок, повторяемые поля/карточки/диалоги. CSS-переменные позволяют менять цвета поверхности, текста и границ без отдельной копии каждого компонента.

[theme.js](../public/theme.js) сначала читает ручной выбор из `localStorage`; если его нет, использует `prefers-color-scheme`. Ставит `data-theme` на корневом элементе до отрисовки React. Изменения темы передаются событием, а React подписывается через [use-theme.ts](../lib/use-theme.ts). Скрипт учитывает изменение системной темы и изменение сохранённого выбора в другой вкладке. При недоступном storage переключение текущей страницы продолжает работать.

`localStorage` используется для пользовательских предпочтений, включая тему/прогресс обучения. Пароль и session cookie аккаунта туда не записываются.

### Адаптивность

Вместо отдельного мобильного приложения используется тот же интерфейс с CSS media queries, Grid и Flexbox. На узких экранах меняются число колонок, расположение действий и навигация. У нижней навигации учитываются отступы и safe area, чтобы она не перекрывала содержимое.

При проектировании важны:

- `min-width: 0` и `minmax(0, 1fr)` для сжатия вложенных элементов;
- перенос длинного текста и отдельное место для иконки/стрелки;
- достаточные промежутки и цели нажатия около 44 px и больше в ключевых действиях;
- читаемые размеры полей; для мобильного ввода используется размер около 16 px там, где это необходимо;
- отсутствие действий, доступных исключительно при hover;
- ограничение высоты меню и прокрутка нужной области;
- проверка длинных русских подписей, а не только коротких заглушек;
- различение намеренной прокрутки таймлайна и переполнения всей страницы.

Например, в мобильной карточке организатора действия уложены в сетку 2×2, а иконки стоят над подписями. Такая компоновка даёт одинаковую структуру кнопок с одной и двумя строками, сохраняя читаемый шрифт.

### Доступность

В коде используются `lang="ru"`, семантические элементы, подписи полей, доступные имена кнопок с иконками, состояния `aria-expanded`, `aria-pressed`, `role="status"`/`alert`, ссылка пропуска к содержимому и видимый фокус. В стилях учитывается уменьшение анимации.

[Modal](../app/ui/dialog.tsx) построен на нативном `<dialog>` с `showModal()`: браузер предоставляет модальный режим и клавиатурное поведение. Компонент блокирует прокрутку страницы и возвращает фокус предыдущему элементу. Escape и клик по фону учитывают возможность закрытия; во время критического сохранения диалог может быть недоступен для случайного закрытия.

Для combobox важны не только красивые подсказки, но и связь поля со списком, активный пункт, выбор клавиатурой и корректная работа касаний.

**Честное ограничение:** наличие ARIA и проверок отдельных сценариев не равно полному аудиту WCAG или подтверждённой поддержке всех скринридеров.

## 14. Безопасность: где проходит граница фронтенда

1. **Аутентификация** отвечает на вопрос «кто пользователь?». Здесь используется серверная сессия Django и cookie. Session cookie настроена `HttpOnly`, `SameSite=Lax`, в production — `Secure`.
2. **Авторизация** отвечает на вопрос «что ему разрешено?». Сервер проверяет роль, владельца события, регистрацию, доступ к эфиру и персональные ссылки.
3. **CSRF** защищает изменяющие запросы при cookie-аутентификации: клиент отправляет токен в заголовке, сервер проверяет его. Это не то же самое, что CORS.
4. **Валидация** на клиенте помогает пользователю, на сервере защищает данные. Запрос можно отправить вручную без UI.
5. **React** экранирует обычные строки в JSX. Это снижает риск вставки HTML в таких местах, но не доказывает отсутствие XSS во всём приложении и его зависимостях.
6. **Секреты** подписи LiveKit, БД, SMTP и другие серверные ключи остаются на сервере. Всё в `public`, JS-сборке и переменных `VITE_*`, использованных при сборке, доступно посетителю. Название `.env` само по себе ничего не скрывает от frontend bundle.
7. **Токены доступа к медиа** могут находиться в браузере, потому что нужны подключению. Это ограниченные разрешения; их нельзя путать с серверным секретом подписи. Персональные приглашения и QR также нужно считать чувствительными.
8. **Списки участников** не должны раздаваться вместе с публичной карточкой всем посетителям. Для них отдельный запрос и проверка прав владельца.

Источник настроек cookie: [settings.py](../backend/config/settings.py). Проверки предметных прав — [services.py](../backend/flow/services.py), доступ к видео — [webinars.py](../backend/flow/webinars.py), [broadcasts.py](../backend/flow/broadcasts.py), [access_keys.py](../backend/flow/access_keys.py).

Отображаемый счётчик свободных мест может устареть между запросами. Только серверная атомарная операция может гарантировать, что два участника не заняли последнее место одновременно.

### Как объяснить уровни тестирования

- **Unit:** входные объекты → расчёт → ожидаемый результат. Например, конец события ровно в полночь или два соседних интервала.
- **Компонентный тест:** рендер React, действия пользователя, ответы замоканного API. Например, ввод категории, ошибка записи, повторный QR, подтверждение обмена.
- **Настоящий браузер:** реальная вёрстка, фокус, прокрутка, viewport и политики браузера. jsdom этого полностью не заменяет.
- **Полный сценарий:** браузер → реальный API → изменение данных → повторное чтение. Для медиа нужны ещё реальная сеть, медиасервер и разные клиенты.

Мок камеры проверяет обработку событий, но не подтверждает, что камера Pixel 9 или Safari действительно подключится на публичном адресе.

## 16. Запуск, размещение и ограничения

### Разработка и production

[scripts/dev.mjs](../scripts/dev.mjs) координирует Django и Vite, применяет миграции локальной базы и при соответствующей настройке запускает видеосервис/обработчик и почтовый worker. Vite по умолчанию работает на `127.0.0.1:5173`, Django — на `127.0.0.1:8000`. [vite.config.mts](../vite.config.mts) проксирует API и страницы авторизации на backend.

Сборка создаёт `dist`. В обычном размещении Django раздаёт собранный интерфейс и обслуживает API; перед ним может стоять HTTPS reverse proxy. Gunicorn — сервер Python-приложения, FFmpeg — обработчик видео, LiveKit — медиасервер. Ни один из них не является React-компонентом.

В репозитории есть отдельная конфигурация Vercel: сборка ресурсов и Django API. Она не означает, что там можно запускать постоянный HTTP-видеокодировщик. Конфигурацию конкретного действующего deployment нужно проверять отдельно; этот документ не подтверждает его текущую доступность.

Общая ссылка должна вести на публичный HTTPS-домен. `localhost` — адрес компьютера, на котором открыт браузер; отправлять такую ссылку другому участнику бесполезно без отдельной сетевой настройки.

### Что честно назвать техническим долгом

- Большой `TFlow`: полезно выделить загрузку данных, маршруты и общие действия.
- `send` возвращает `Promise<any>`: типы предметных сущностей есть, но API-клиент можно сделать точнее и добавить runtime-проверку ответа.
- Polling проще поддерживать, но создаёт задержку и дополнительные запросы. При росте нагрузки стоит измерить её и рассмотреть серверные события/управляемый кеш.
- Bootstrap получает сразу несколько наборов данных. Для большого каталога понадобятся серверные поиск, фильтрация и пагинация.
- Крупные медийные JS-части и значительный собственный CSS требуют дальнейшего анализа загрузки и каскада.
- Ручной hash-router имеет ограничения по метаданным и усложняет сопровождение сложной навигации.
- Временная модель ориентирована на МСК.
- HTTP/HLS подходит для трансляции; он имеет задержку, потребляет ресурсы кодирования и не заменяет все функции интерактивной встречи.
- Нет основания обещать полноценную офлайн-работу, установленную PWA, Web Push, автоматическую синхронизацию календаря или аудит доступности: наличие обычного веб-интерфейса этого не обеспечивает.

Следующий шаг выбирают по измеренной проблеме: например, сначала пагинация растущего каталога, а не подключение Redux только ради дополнительной технологии.

## 18. 60 вопросов с ответами

Ответы рассчитаны на разговор, а не на заучивание терминов. После короткого ответа полезно показать конкретный сценарий или функцию.

### Архитектура и инструменты

**1. Почему React?**

У нас много связанных состояний: фильтры, запись, модальные формы, программа и медиа. Компоненты позволяют повторять одинаковое поведение и обновлять отображение из состояния. Это удобство разработки; само по себе оно не гарантирует максимальную скорость приложения.

**2. Почему не обычный JavaScript без React?**

Так тоже можно реализовать продукт, и страницы авторизации частично так и работают. Для основной интерактивной части ручная синхронизация DOM между несколькими состояниями была бы сложнее; React задаёт единый способ описания UI.

**3. Зачем TypeScript, если есть тесты?**

Типы ловят несовместимые аргументы и свойства до запуска. Тесты проверяют поведение на конкретных примерах. Они дополняют друг друга: правильный тип времени `number` ещё не гарантирует правильный часовой пояс.

**4. Что даёт `strict`?**

Более строгую статическую проверку, включая явную работу с возможным `null` и типами функций. Но `any` ослабляет эту защиту; текущий общий API-клиент — пример места для улучшения.

**5. Зачем Vite?**

Для разработки и подготовки браузерных ресурсов: TSX, CSS, импорты и production-сборка. API и хранение данных выполняет Django, а не Vite.

**6. Это SPA или SSR?**

Основная часть — клиентская SPA: React строит экраны в браузере после получения данных. Django отдельно рендерит формы авторизации. Серверного рендера React-страниц в текущей архитектуре нет.

**7. Почему не Next.js?**

Текущему приложению достаточно React SPA и уже существующего Django API. Next.js мог бы дать другие возможности для SSR и маршрутов, но добавил бы отдельные архитектурные обязанности. Мы не заявляем, что он принципиально хуже.

**8. Зачем Node, если сервер на Python?**

Node запускает сборщик и тесты фронтенда. Готовые JS/CSS может раздавать Django; Node не обязательно остаётся в production runtime.

**9. Почему нет Redux?**

Общие данные сейчас находятся в корневом компоненте, локальные — у компонентов. Для такого устройства хватает React hooks. Если связи усложнятся, сначала стоит отделить серверное состояние и измерить проблему, затем выбирать инструмент.

**10. Как работает навигация без React Router?**

Маршрут читается из hash, список разделов проверяется вручную, `hashchange` обновляет состояние. Это простой способ делиться ссылками, но поддержку вложенных маршрутов и ошибок мы берём на себя.

### Состояние, API и ошибки

**11. Что вызывает повторный рендер?**

Обновление состояния, изменение props и подписанных значений. Запись в `ref.current` сама рендер не запускает; поэтому ref подходит для медиаресурса, но не как замена состоянию видимого текста.

**12. Чем props отличаются от state?**

Props передаёт родитель, state хранит сам компонент. Например, серверное событие приходит как prop, а открытый список категорий хранится локально.

**13. Зачем `useEffect` и очистка?**

Для внешних подписок и ресурсов: запросов, таймеров, медиа. Очистка удаляет слушатель, останавливает трек или отменяет запрос при уходе и перед повторным запуском эффекта.

**14. Чем контролируемое поле отличается от неконтролируемого?**

У контролируемого значение задаётся React state и меняется обработчиком. У неконтролируемого текущим значением управляет DOM; его можно получить через `FormData`. В проекте есть оба подхода в зависимости от нужного взаимодействия.

**15. Почему Fetch, а не Axios?**

Текущие потребности закрываются встроенным Fetch и небольшим общим клиентом. Для JSON, cookie, CSRF и обработки ошибок дополнительная библиотека не обязательна.

**16. Как обрабатывается ошибка API?**

Проверяется HTTP-статус, тело превращается в `ApiError`. Форма может показать ошибки полей, запись — запросить недостающий профиль, а экран — сообщение или повторную попытку.

**17. Почему поздний ответ не показывает чужое событие?**

Загрузчики сравнивают номер завершившегося запроса с актуальным. Старый ответ игнорируется. Это особенно важно при быстром переключении между карточками.

**18. Зачем повторно загружать данные после записи?**

Сервер мог изменить не только факт записи, но и места, очередь, календарь и счётчики. Повторное чтение получает согласованное состояние. Цена — дополнительные запросы и ожидание.

**19. Как приходят обновления без WebSocket?**

Обычные данные периодически перечитываются и обновляются при фокусе. У эфира и чата свои интервалы. Это polling с некоторой задержкой, а не обещание мгновенной доставки.

**20. Что происходит при плохом интернете или двойном клике?**

Показываются загрузка и ошибки, кнопки ограничивают повторное действие; у медиазагрузки есть таймауты и ограниченные повторы. Абсолютную защиту от повторной записи или гонки обеспечивают серверные правила, не кнопка `disabled`.

### Программа и календарь

**21. Чем мероприятие отличается от активности?**

Мероприятие задаёт общие время, формат и регистрацию. Активность — пункт внутри него с аудиторией, спикером, собственным временем и местами.

**22. Как определяются пересечения?**

Начало A раньше конца B, и конец A позже начала B. Соседние интервалы, соприкасающиеся ровно границей, совместимы. Проверки есть на клиенте для UX и на сервере для сохранения.

**23. Как флоу размещает параллельные активности?**

Сортирует интервалы, объединяет связанные пересечения и выдаёт первую свободную колонку. Одновременные интервалы находятся рядом; освободившаяся колонка используется повторно.

**24. Почему шкала включает пустое время?**

В раскладку передаются границы всего мероприятия. Пауза — часть временного контекста, и её отсутствие искажало бы представление о продолжительности события.

**25. Почему короткий блок иногда визуально крупнее его линейной высоты?**

Для читаемости подписи есть дополнительная обработка раскладки. Реальные начало и конец сохраняются; доступные пользователю значения времени нельзя подменять визуальной высотой.

**26. Откуда берутся цвета?**

ID активности преобразуется в индекс общей палитры. Это даёт стабильность между обновлениями. Цвет дополняет название и время, но не должен быть единственным способом различать события.

**27. Как работает линия текущего времени?**

Текущая временная отметка переводится в координату флоу. Подпись показывает МСК; обновление привязано к минуте и границам программы, а при возврате во вкладку время пересчитывается.

**28. Как перетаскивание становится новым временем?**

Координата указателя переводится в долю временного диапазона, округляется к шагу и ограничивается границами мероприятия. После предпросмотра изменение отправляется серверу, который проверяет конфликты заново.

**29. Как защищён обмен пунктов программы?**

Сначала серверный предпросмотр, затем явное подтверждение с ожидаемой версией события. Если кто-то успел изменить расписание, сервер может отклонить устаревшее действие.

**30. Что такое optimistic concurrency?**

Проверка, что версия данных не изменилась с момента чтения. Это не предварительное изображение успеха в UI; такое поведение называется optimistic update.

**31. Как календарь работает с полуночью?**

Разделяет отображение по московским дням и обрезает интервал по границам дня. Конец ровно в 00:00 не добавляет запись на следующий день; исходные временные отметки не меняются.

**32. Почему не использовать часовой пояс устройства?**

Программа события должна показывать одно и то же время разным участникам. Сейчас продукт ориентирован на МСК, поэтому форматирование и ввод используют её явно. Произвольные зоны — отдельное расширение.

**33. Что делает экспорт в календарь?**

Скачивает `.ics`, сформированный сервером. Внешний календарь может импортировать файл. Это снимок, а не постоянная двусторонняя синхронизация.

**34. Как не продать последнее место двум пользователям?**

Клиент показывает актуальное на момент чтения число мест, но не решает гонку. Сервер должен проверять и сохранять запись атомарно; после ответа UI перечитывает состояние.

### QR и медиа

**35. Что лежит в QR и кто принимает решение о входе?**

В коде используется токен личного пропуска. Браузер декодирует его и отправляет для выбранного мероприятия; сервер проверяет регистрацию и права организатора.

**36. Почему сначала надо выбрать событие в сканере?**

Участник может быть записан на несколько мероприятий, а его QR — личный. Серверу нужен конкретный контекст, где проверять регистрацию и отмечать вход.

**37. Почему QR нельзя бесконечно засчитывать повторно?**

Сервер хранит факт входа на мероприятие и возвращает состояние повторной проверки. Клиентская блокировка лишь уменьшает поток одинаковых запросов из видеокадров.

**38. Почему камера не работает по обычному HTTP с телефона?**

Браузер ограничивает доступ к устройствам защищённым контекстом и разрешением пользователя. Публичному приложению нужен HTTPS; localhost на ноутбуке не является localhost телефона.

**39. Что делать без камеры?**

В сканере есть загрузка QR-изображения и ручной ввод содержимого. Ошибка разрешения не должна лишать организатора всех путей проверки.

**40. Почему для вебинара выбрали LiveKit?**

Клиент предоставляет готовую модель комнат, треков и подключения WebRTC. Это уменьшает объём собственной реализации медиасигналинга и доставки, но требует отдельной правильно настроенной инфраструктуры.

**41. Зачем понадобился HTTPS/HLS-режим?**

Чтобы передавать эфир через обычные HTTP-маршруты приложения при ограничении медиапортов. Ведущий отправляет фрагменты, FFmpeg создаёт HLS, зритель воспроизводит его. Цена — задержка и серверное кодирование.

**42. Чем HLS отличается от WebRTC-встречи?**

HLS — доставка сегментированной трансляции с буфером. WebRTC рассчитан на интерактивные медиасоединения. Наш HTTP-режим нельзя выдавать за полноценную встречу, в которой все зрители одновременно публикуют свои камеры.

**43. Почему HTTP-видео нельзя просто перенести в Vercel-функцию?**

Текущий путь требует постоянно работающего FFmpeg worker и общего хранилища сегментов. Короткоживущая обработка запроса не заменяет этот процесс; код проекта отключает данный режим на Vercel.

**44. Как разнесены параллельные эфиры и права лектора?**

Эфир связан с мероприятием или отдельной онлайн-активностью. Персональная ссылка лектора ограничена своей активностью, проверяется сервером и не даёт весь кабинет организатора.

**45. Почему браузер иногда требует нажать «подключиться» для звука или экрана?**

Это политики autoplay и разрешений на захват. Пользовательское действие должно происходить до соответствующего вызова; интерфейс объясняет отказ и предлагает повторить действие.

**46. Что освобождается после выхода из студии?**

Собственные медиатреки, загрузка фрагментов, таймеры, обработчики и экземпляр HLS/комнаты по своему жизненному циклу. Без очистки можно оставить микрофон занятым или передачу в фоне.

### UX, безопасность и качество

**47. Почему категории не обычный длинный select?**

Нативный огромный список неудобен при большом числе тем, особенно на телефоне. Поиск с ограниченной выдачей позволяет найти любую категорию, не раскрывая весь справочник на экран.

**48. Почему нельзя просто сохранить введённое слово как категорию?**

Категории — согласованный справочник для фильтрации. Поиск помогает выбрать его значение, а не создаёт новую категорию. Свободный текст мог бы породить десятки вариантов одной темы.

**49. Почему профиль необязательный, а при записи вдруг нужны данные?**

Это разные этапы. Базовый профиль можно заполнить позже, но организатор конкретного события вправе запросить предусмотренные дополнительные поля. Сервер возвращает список недостающего именно для этой записи.

**50. Как сделана тёмная тема без вспышки светлой?**

Небольшой скрипт выставляет `data-theme` ещё до React по сохранённому выбору или настройке системы. CSS-переменные задают соответствующие цвета.

**51. Как проверяли удобство на телефоне?**

Компоненты адаптируются CSS-правилами: колонки, отступы, навигация, размер целей нажатия и переносы. Исторические браузерные проверки описаны отдельно. Тест jsdom сам не доказывает корректность вёрстки на физическом Pixel или iPhone.

**52. Что сделано для доступности?**

Подписи, семантика, доступные имена кнопок, видимый фокус, статусы, клавиатурный выбор и нативный модальный dialog с возвратом фокуса. Полный аудит WCAG мы не заявляем.

**53. Где хранится авторизация и зачем CSRF?**

Авторизация связана с серверной сессией и HttpOnly cookie, а не JWT в localStorage. При изменяющих запросах CSRF-токен подтверждает допустимость запроса в этой cookie-схеме; сервер всё равно проверяет права.

**54. Можно ли получить права, просто показав скрытую кнопку?**

Нет, если серверные проверки выполнены правильно. Клиентский интерфейс облегчает работу, но роль, владелец, запись и доступ к эфиру проверяются сервером на запросе.

**55. Почему нельзя хранить секрет LiveKit в `VITE_*`?**

Значения, использованные frontend-сборкой, доступны браузеру. Серверный секрет подписи должен оставаться на сервере; клиент получает только разрешённый токен подключения.

**56. Что реально проверяют тесты?**

Расчёты времени и интервалов, поведение форм, фильтров, записи, QR, программы и медиаошибок. Моки подтверждают обработку сценария, но не работоспособность настоящей камеры, сети и публичного видеосервера.

**57. Сколько тестов прошло?**

На проверке этого документа — 275 Vitest-тестов в 47 файлах и 36 дополнительных Node-тестов. TypeScript и production build тоже прошли. Это результат конкретной версии, не обещание покрытия 100% кода.

**58. Какие есть проблемы производительности?**

Сборка предупреждает о крупных медийных частях. Есть lazy loading, но нужен дальнейший анализ размера, CSS и поведения на слабых устройствах. Масштабирование bootstrap и polling тоже потребует измерений.

**59. Что улучшили бы следующим шагом?**

Разделили бы корневой компонент и типизировали API-ответы, затем по измерениям улучшали загрузку и пагинацию. Для видео — отдельная проверка реальных устройств, сети и нагрузки. Выбор зависит от проблемы, а не от желания добавить модную библиотеку.

**60. Как доказать, что функция работает?**

Показать полный путь: действие в браузере, успешный запрос, изменение серверных данных и результат у другого пользователя/после обновления. Для эфира — ведущего и зрителя на разных клиентах через публичный HTTPS-адрес. Одной зелёной кнопки или запуска на localhost недостаточно.

## 19. Демонстрация на защите

Заранее подготовить отдельные аккаунты участника и организатора, мероприятие с несколькими аудиториями, пересекающимися и короткими активностями. Не показывать пароли, служебные ключи, полный личный QR или реальные данные посторонних людей в открытом выступлении.

### Сценарий на 7–10 минут

1. **Каталог:** поиск, компактный выбор категории, фильтры. Объяснить отличие пустой выдачи от ошибки.
2. **Карточка события:** общие рамки мероприятия и внутренняя программа.
3. **Участник:** запись, недостающие поля при необходимости, активность без конфликта и пример предупреждения о пересечении.
4. **Флоу:** параллельные активности, длительность, весь интервал события, цвет и текущее время.
5. **Календарь:** выбранные события/активности, день и `.ics`.
6. **Организатор:** аудитории, редактирование времени, предпросмотр обмена и подтверждение.
7. **QR:** выбранное мероприятие, первое и повторное считывание на тестовом участнике.
8. **Видео:** отдельные ведущий и зритель, рабочий транспорт, микрофон/камера/экран, сообщение чата. Сказать, какой транспорт используется именно в этой демонстрации.
9. **Телефон и тема:** основные действия, меню категории, диалог, отсутствие перекрытия нижней навигацией.

### Что проверить заранее

- Публичная ссылка ведёт на правильный deployment; в настройках нет адреса localhost для чужих браузеров.
- Backend, БД и нужный медиасервис действительно доступны, а не только страница HTML.
- Браузеру разрешены камера/микрофон; для экрана есть поддерживаемый способ захвата.
- Для HTTP-видео работает worker; для LiveKit — его сетевые маршруты и TLS.
- Две роли открыты в разных профилях браузера, чтобы не перепутать cookie.
- Известен путь восстановления: повторная загрузка данных, повторное разрешение устройств, загрузка QR-файла вместо камеры.

Если не помнишь деталь, лучше ответить: «Принцип такой-то; точный порог/вариант нужно сверить в этом модуле». Не приписывать фронтенду серверную гарантию и не выдавать тест с моками за проверку реальной сети.

## 20. Мини-словарь

- **SPA** — клиентское приложение, меняющее экраны без полной перезагрузки HTML на каждое действие.
- **DOM** — дерево элементов страницы, с которым работает браузер.
- **JSX/TSX** — синтаксис описания интерфейса внутри JS/TypeScript; браузер получает уже собранный JavaScript.
- **CSR / SSR** — построение интерфейса в браузере / на сервере.
- **State / props / ref** — состояние компонента / входные параметры / изменяемая ссылка без самостоятельного рендера.
- **Race condition** — результат зависит от порядка конкурирующих операций; пример — поздний ответ старого запроса.
- **Polling** — периодические запросы за обновлениями.
- **Debounce** — задержка обработки до паузы во вводе; не нужно заявлять, что она есть у каждого поиска, если код фильтрует сразу.
- **Lazy loading / chunk** — загрузка части кода при необходимости / отдельный выходной файл сборки.
- **CSRF / XSS / CORS** — разные задачи: подделка запроса с cookie / выполнение внедрённого скрипта / правила доступа браузера между origin.
- **Origin** — сочетание схемы, хоста и порта; `localhost:5173` и `localhost:8000` имеют разные origin, поэтому dev proxy полезен.
- **WebRTC / SFU** — браузерная технология интерактивных медиа / сервер пересылки потоков.
- **MediaStream / track** — набор медиатреков / отдельный источник звука или видео.
- **MediaRecorder** — браузерная запись/кодирование медиапотока в фрагменты.
- **HLS** — доставка видео через плейлист и последовательность HTTP-сегментов.
- **FFmpeg** — серверный инструмент обработки и перекодирования медиа.
- **Optimistic concurrency** — проверка ожидаемой версии перед изменением данных.
- **Responsive UI** — адаптация одной страницы к разным размерам и способам ввода.
