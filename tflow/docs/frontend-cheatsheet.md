# ТФлоу: шпаргалка по фронтенду

Версия кода: `gosha`, исходный коммит `ffae101`, проверено 1 ноября 2026 года. Подробности, карта файлов и 60 вопросов: [полная документация](frontend-defense.md).

## Рассказ на минуту

> Фронтенд ТФлоу написан на React и TypeScript. Мы объединяем поиск событий, запись, персональную программу, календарь, QR-вход и онлайн-эфиры. Самая содержательная часть — программа с параллельными активностями: нужно понятно показать время, длительность и пересечения. Расчёты вынесены в отдельные функции и проверяются независимо от компонентов. React управляет интерфейсом, а Django проверяет права, места и сохранение. Есть адаптация под телефон, светлая и тёмная темы. Для медиа поддержаны LiveKit/WebRTC и отдельный HTTPS/HLS-режим: второй помогает при ограниченных медиапортах, но является трансляцией с задержкой, а не полноценной заменой интерактивной встречи.

## Стек: что и зачем

- **React 19.2.6:** компоненты и обновление UI из состояния.
- **TypeScript 5.9.3, strict:** проверка структуры данных и параметров при разработке. Не проверяет автоматически JSON с сервера.
- **Vite 8.1.6:** dev server, обновление при разработке и production-сборка. Не backend.
- **Собственный CSS + подключённый Tailwind 4.2.1:** адаптивная вёрстка, общие переменные, компоненты и темы. Не весь UI написан utility-классами.
- **Golos + Lucide:** локальный шрифт и согласованные SVG-иконки.
- **Fetch:** HTTP, cookie, JSON/FormData и CSRF через общий клиент.
- **ZXing:** декодирует QR; решение о входе принимает сервер.
- **LiveKit:** клиент комнат и медиатреков WebRTC.
- **hls.js:** проигрыватель HLS там, где используется соответствующая поддержка браузера.
- **Vitest + Testing Library + jsdom:** расчёты и поведение компонентов; это не физическое устройство.

Отдельных Redux, React Router, Next.js и Axios в текущем приложении нет. Node нужен для разработки/сборки, собранный интерфейс может раздавать Django.

## Архитектура за 30 секунд

```text
index.html → main.tsx → GET /api/auth/me → TFlow
  TFlow → /api/bootstrap → экраны app/ui
  lib → типы, время, пересечения, раскладка, медиавспомогательные функции
  fetch /api/… → Django → база данных
```

Основная часть — React SPA с hash-маршрутами: `/#events`, `/#event/<id>`, `/#calendar`, `/#manage/<id>`. Вход и регистрация — Django HTML-формы с JavaScript и общим оформлением.

В `TFlow` находятся общие данные и действия; локальное состояние форм/меню остаётся в компонентах. Большой корневой компонент — известное место для дальнейшего разделения.

## Что нужно понимать по функциям

**Мероприятие и активность.** Мероприятие — общие рамки, владелец и регистрация. Активность — пункт программы с временем, аудиторией, спикером и местами. Это не одна сущность.

**Запросы.** Общий `send` передаёт cookie, JSON или FormData, добавляет CSRF для изменения. Ошибка содержит сообщение, код и иногда ошибки полей/недостающие данные. После успеха данные перечитываются. Номера запросов защищают от устаревшего ответа.

**Обновления.** Для участника в профиле/событии polling раз в 5 секунд, иначе — 15 секунд с учётом видимости; есть обновление при фокусе. Это не мгновенные серверные события.

**Флоу.** Время превращается в вертикальную координату, длительность — в высоту. Пересекающиеся интервалы получают колонки. Показывается весь диапазон мероприятия, включая паузы. Дополнительная раскладка делает короткие карточки читаемыми, не меняя реальные времена. Цвет стабилен по ID. Красная линия показывает текущее московское время цифрами.

```text
Пересечение: начало A < конец B И конец A > начало B.
10:00–11:00 и 11:00–12:00 не конфликтуют.
```

**Редактор.** Координата указателя переводится во время, округляется к шагу и ограничивается рамками события. Есть ввод точных значений. Обмен пунктов: серверный предпросмотр → подтверждение с ожидаемой версией → обновление. Проверка версии — optimistic concurrency, не optimistic UI.

**Календарь.** Объединяет билеты, выбранные активности и свои события. Обрабатывает полночь, колонки и месяцы. Время отображается в МСК независимо от зоны устройства. `.ics` — экспорт файла, не постоянная синхронизация с Google Calendar.

**Профиль.** В редакторе обязательна учётная почта, она только для чтения; остальные поля можно не заполнять. При записи организатор может запросить дополнительные поля: API вернёт `PROFILE_INCOMPLETE` и их список. Это отдельное правило конкретной записи.

**Категории.** Один общий справочник, поиск по названию/группе и предусмотренным синонимам. Одна категория выбирается в компактном combobox; несколько интересов — тегами. Ввод поиска сам по себе не создаёт категорию. Список ограничен по высоте и управляется клавиатурой/касанием.

**QR.** Выбрать событие → распознать токен камерой/изображением → API проверяет права, регистрацию и предыдущий вход. Повторный QR не должен увеличивать счётчик. Камере нужны HTTPS/localhost и разрешение. Личный QR можно скопировать: он не доказывает личность предъявителя.

## Видео: самый важный сложный вопрос

**LiveKit:** Django выдаёт ограниченный токен → браузер подключается к медиасерверу → WebRTC-треки. LiveKit — SFU, пересылающий потоки. Нужны рабочая сеть, публичный адрес и TLS. `localhost` в настройке чужого клиента указывает на его компьютер.

**HTTPS/HLS:** камера/экран + звук → canvas/Web Audio → MediaRecorder → HTTP-фрагменты → постоянный FFmpeg worker → HLS → зритель. Не требует отдельных публичных медиапортов, но требует работающего сервера приложения, worker и хранилища. Есть буфер и задержка. По умолчанию сервер допускает до двух одновременных HTTP-эфиров; нагрузочное масштабирование этим не доказано.

Режим выбирает серверная конфигурация/статус, а не автоматическая замена при любой ошибке. В текущем проекте HTTP-транспорт отключён на Vercel, потому что ему нужен постоянный кодировщик. У онлайн-активностей раздельные эфиры. Ссылка лектора даёт ограниченный доступ к своей активности после входа в аккаунт, не всю роль организатора.

Чат и статусы HTTP-компонента обновляются polling. Камера/микрофон, autoplay и показ экрана ограничиваются браузером. При выходе нужно остановить треки, загрузку, таймеры и плеер. Моки медиа не доказывают работу публичного эфира.

## Безопасность и доступность

- Серверная сессия — в HttpOnly cookie; пароль не в localStorage. В production cookie защищена `Secure`; CSRF-токен передаётся для изменяющих запросов.
- Скрытая кнопка не защищает API. Роль, владелец, места и доступ к эфиру проверяются Django.
- TypeScript и проверка формы помогают разработке/UX; запрос можно отправить без них.
- Серверный секрет подписи LiveKit и пароли БД/SMTP нельзя помещать в `VITE_*` или `public`: frontend-ресурсы доступны посетителю.
- Публичный HTTPS нужен для устройств; открывшаяся HTML-страница не доказывает доступность WebRTC-медиа.
- Есть подписи, видимый фокус, статусы, клавиатурный выбор, native dialog с возвратом фокуса. Полный аудит WCAG не заявлен.
- Тема применяется до React по ручному выбору или настройке устройства, затем меняется через CSS-переменные.
- На телефоне важны переносы, размер целей нажатия, интервалы, safe area и отдельная прокрутка таймлайна. jsdom реальную геометрию не проверяет.

## Проверки и ограничения

1 ноября 2026 в рабочей копии от `ffae101`: **275 Vitest-тестов + 36 Node-тестов = 311 проверок**, TypeScript и production build прошли. Серверные тесты в этой проверке документа не запускались.

Сборка предупреждает о крупных медийных JS-частях. Есть lazy loading, но нельзя заявлять идеальную производительность или покрытие 100%. Другие ограничения: большой `TFlow`, `Promise<any>` у API-клиента, ручной роутер, polling, загрузка нескольких наборов bootstrap, привязка к МСК, зависимость медиа от инфраструктуры.

Из `tflow`:

```bash
npm run check
npm run test:frontend
npm run build
# Отдельно:
npm run test:backend
```

## Что показать и чего не обещать

Демо: каталог → категория → карточка → запись → конфликт активностей → флоу → календарь → организаторский редактор → первый/повторный QR → ведущий и зритель на публичном эфире → телефон/тема.

Не называть:

- HLS-трансляцию полноценной многопользовательской WebRTC-встречей;
- `.ics` двусторонней синхронизацией;
- скрытие кнопки серверной защитой;
- TypeScript проверкой данных сети во время выполнения;
- тесты с моками испытанием реальной камеры и сети;
- hash-router SSR или готовой SEO-архитектурой;
- прохождение сборки доказательством работы всех production-сервисов;
- два разрешённых HTTP-эфира доказанной нагрузочной ёмкостью системы.

Формула хорошего ответа: **задача пользователя → наше решение → конкретный механизм → ограничение → как проверяли**.

Если забыта деталь: «Принцип такой-то; точный параметр проверю в этом модуле». Основные файлы: `app/tflow.tsx`, `lib/types.ts`, `lib/flow-layout.ts`, `lib/calendar.ts`, `app/ui/qr-scanner.tsx`, `app/ui/webinar.tsx`, `app/ui/http-webinar.tsx`.
