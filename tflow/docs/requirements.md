# ТФлоу: соответствие EventFlow

Backend: Python/Django 5.2, Django ORM, SQLite локально; конфигурация PostgreSQL для production. Frontend: React 19, TypeScript, Vite. Жёлто-белый стиль сохранён. Рекламных баннеров нет.

## Сохранение прежних данных

`manage.py import_d1` использует read-only соединение и SQLite backup для согласованного снимка с учётом WAL. Импортирует пользователей, сообщества, события, аудитории, активности, регистрации, избранное, членства и уведомления в одной транзакции. Прежние идентификаторы сохраняются. Существующие Django-строки не перезаписываются; финальная проверка предотвращает создание конфликтов. У импортированных пользователей нет пригодного для входа пароля.

`npm run setup` применяет только миграции. Автоматический импорт и демо-наполнение удалены; `import_d1` доступен только как отдельная явно запускаемая команда. Live D1 из архивной публикации автоматически не экспортируется.

## Блокировки

Все изменения программы, аудиторий, дат события, запись и отмена используют `schedule_write()`. SQLite IMMEDIATE захватывает блокировку записи до чтения ограничений. PostgreSQL сериализует эти операции через `SELECT FOR UPDATE` одной строки. Это простое решение для MVP с сотнями участников; транзакции короткие и не включают сетевые операции. Для многорепличного production нужна общая PostgreSQL, не независимые SQLite-файлы.

Лист ожидания реализован: очередь на заполненные активности, автоматическая запись при освобождении места и уведомление. Автоматическое распределение аудиторий пока не включено. QR отмечает вход на событие; отдельной отметки на каждую активность из дополнительного раздела 6 пока нет. В скачиваемом ICS есть напоминание за 30 минут; серверных отложенных напоминаний нет. Платежи и видеотрансляции ТЗ не требует.

Источники: [Django databases](https://docs.djangoproject.com/en/5.2/ref/databases/), [Django authentication](https://docs.djangoproject.com/en/5.2/topics/auth/default/), [Django CSRF](https://docs.djangoproject.com/en/5.2/ref/csrf/), [Leader-ID](https://leader-id.ru/events).

## Роли, билеты и посещаемость (версия 0.3)

- `User.role`: participant или organizer. Административные сервисы проверяют роль и владельца события на сервере. Старые владельцы событий повышены до organizer миграцией; обычный PATCH профиля роль не меняет.
- `EventRegistration`: билет на событие, создаваемый одной кнопкой. Запись на отдельную активность также гарантирует билет на событие. Отмена билета удаляет собственные записи на активности, если вход ещё не подтверждён.
- `CheckIn`: одна отметка на пару user/event. QR содержит только случайный UUID профиля; контакты не зашиты в изображение.
- Сканер получает контекст конкретного события. При наличии билета сохраняет отметку; при отсутствии возвращает отказ без раскрытия личных данных. Повторный скан идемпотентен.
- `PATCH events/:id/move`: под общей транзакционной блокировкой сдвигает все активности на одинаковую дельту, проверяет границы и внешние конфликты, переносит площадку и уведомляет всех владельцев билетов.
- Мобильные сценарии: каталог → одна кнопка регистрации → билет → личный QR. Организатор: список событий → перенести / сканировать → список зарегистрированных и вошедших. Подробная программа спрятана в дополнительный блок.

QR-посещаемость и лист ожидания реализованы. Автоматическое распределение аудиторий пока не добавлено.

## Дополнения по исходному EventFlow.pdf

- Один постоянный QR относится к профилю и доступен в профиле обеим ролям. Один и тот же код предъявляется на всех событиях; организатор сканирует его в контексте своего события, а сервер проверяет регистрацию. Изменение роли и запись на новые события не создают новый код.

- Минимальный размер текста интерфейса — 12 px (`--font-size-min`), включая мобильные подписи, метки, подсказки и формы входа/регистрации. На узких экранах высота нижнего меню учитывается в отступах закреплённой панели регистрации.

- Город выбирается через автодополнение в профиле, создании/редактировании/переносе события и фильтре каталога. Поиск по части названия без учёта регистра, пробелов, дефисов и ё/е; поддержаны «спб», «Питер» и «мск». Выбор мышью или ↑/↓ и Enter, закрытие Escape и очистка поля. В профиле и событиях доступны предложенные города и собственное название; в фильтре подсказки берутся из текущих событий.

- При регистрации и редактировании профиля имя и фамилия вводятся отдельно и сохраняются в `User.first_name`/`User.last_name`. `User.name` обновляется одновременно для отображения полного имени в профиле, билетах и списках. Старое полное имя используется для начального заполнения пустых отдельных полей; прежний формат API с `name` остаётся совместимым.

- Интересы профиля выбираются из категорий при регистрации и редактировании. Допускаются несколько тем или пустой выбор. Ранее сохранённые свободные интересы остаются доступны, названия AI/ИИ приводятся к категории «Искусственный интеллект» в интерфейсе. Регистрация, React и каталог используют общий список из `backend/flow/interest_categories.json`.

- Лист ожидания доступен для заполненных будущих активностей. При вступлении оформляется билет на событие; место на активности ещё не занято. Вступление и выход относятся только к текущей сессии пользователя.
- Очередь FIFO с повторной проверкой пересечений. Участник с конфликтом сохраняет очередь, а место получает следующий подходящий участник. После отмены конфликта или изменения программы свободные места проверяются снова. Увеличение лимита также обрабатывает очередь. После начала активности автоматическая запись закрыта.
- Отмена билета удаляет собственные записи и очереди в этом событии. Все операции выполняются под общей транзакционной блокировкой, уведомление о получении места сохраняется в той же транзакции.
- В программе есть поиск по названию/спикеру, фильтры по аудитории и дню, показ свободных мест и предупреждение о пересечении до отправки запроса. «Моя программа» доступна из основной навигации и показывает подтверждённые записи и лист ожидания.
- Календарь: `.ics` для события и личных подтверждённых активностей. UTC, стабильные UID, UTF-8 folding и напоминание за 30 минут. Это скачиваемый снимок, не подписка: после изменения программы файл нужно скачать снова.
- Аватар профиля: JPG/PNG/WebP до 5 МБ и 16 Мп; предпросмотр, центральная обрезка до 384×384 и удаление. Сервер декодирует изображение, пересохраняет в WebP без исходных метаданных и хранит в БД, включая Vercel/PostgreSQL. Чтение и изменение доступны только владельцу профиля; фото отображается в шапке и профиле.

Референс мобильных паттернов: [Airbnb](https://www.airbnb.com/). Камера и декодер: [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [ZXing browser](https://github.com/zxing-js/browser).

## Политика конфликтов EventFlow (§5.5 и §8)

Выбран вариант полного отклонения изменения с конфликтом. Автоматического снятия участников с записи и скрытого превышения вместимости нет. Проверка обязательна на сервере; подсказка в интерфейсе лишь заранее объясняет ограничение.

- Интервалы полуоткрытые: 10:00–11:00 и 11:00–12:00 совместимы. Совпадение, частичное пересечение и вложение запрещены.
- Аудитория проверяется внутри события: в одной аудитории одновременно допустима одна активность. Лимит активности не превышает вместимость аудитории и не может стать меньше числа уже записанных.
- Личное расписание проверяется по всем активностям участника во всех событиях. Билеты на события не занимают время активности: билет на конференцию может пересекаться с её лекциями.
- При изменении времени или аудитории проверяются все записанные участники. Перенос события сдвигает всю программу на одинаковую дельту и проверяет внешние записи участников.
- Ошибка откатывает все поля, записи и уведомления одной транзакцией. Успешный перенос сохраняет регистрации и обновляет личное расписание.
- Создание, изменение, запись и отмена используют общую блокировку. Гонки записи с уменьшением лимита, переносом, дублем и освобождением последнего места не нарушают ограничения.

## Проверка 30 октября 2026

По обязательным разделам §5.1–5.6, §8 и демонстрационному сценарию §10 реализованы события, аудитории, программа, роли, запись, отмена, вместимость, личное расписание и безопасное изменение программы. Дополнительные функции §6 не считаются условиями готовности MVP.

Исправлены сброс необязательных полей события при редактировании (включая лимит, который мог самопроизвольно стать 500), отсутствие свободных мест в программе участника и отсутствие отмены активности из календаря. Программа упорядочена по времени начала. Карточка календаря получает актуальные данные при обновлении расписания.

Автоматическая проверка: 180 тестов Django, 15 тестов календаря, 8 тестов доступности активностей; TypeScript и production-сборка. Регрессионные проверки границ и конкуренции находятся в `backend/flow/tests/test_spec_conflicts.py`. Конкуренция проверена на SQLite; исполнение на реальном PostgreSQL требует отдельного окружения и в этот результат не включено.

Ручной сценарий на изолированной базе: через UI созданы событие, две аудитории и три активности; проверены соседние интервалы, запрет пересечений, свободные места и отмена из календаря. Через форму организатора проверены отклонение переноса в занятый зал, конфликт у участника и успешный перенос на свободное время. При отказе исходные время, аудитория, записи и уведомления сохранены без изменений. Тёмная и светлая темы проверены в приложении и формах авторизации, на ширине телефона и компьютера.

Команды: `npm run test:backend`, `npm run test:frontend`, `npm run check`, `npm run build`. Для ручной проверки используются отдельная SQLite-база и тестовые аккаунты, без наполнения рабочей базы демонстрационными событиями.
