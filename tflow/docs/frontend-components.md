# Фронтенд ТФлоу: объяснение компонентов и решений

По локальной версии проекта на 1 ноября 2026 года. Новые модули из локальной интеграции могут ещё отсутствовать в удалённой ветке.

Здесь объясняется, **что делают части нашего фронтенда и почему такой способ реализации подходит проекту**. Альтернативы приводятся для сравнения, а не потому, что они плохие. Это разбор существующего кода, а не утверждение, что команда экспериментально сравнила все технологии.

## 1. Сначала понять, что такое компонент

Компонент React — функция, которая описывает часть интерфейса. Например, `ActivityCard` описывает карточку активности, а `Calendar` — календарь. Компонент получает данные и обработчики действий через **props** и может хранить собственное изменяемое состояние — **state**.

Упрощённый пример с нашим компонентом:

```tsx
<ActivityCard
  activity={activity}
  schedule={schedule}
  organizer={false}
  pending={pending}
  onAction={handleAction}
/>
```

`activity` сообщает, что показать; `schedule` помогает обнаружить пересечение с личной программой; `pending` показывает, выполняется ли действие; `onAction` сообщает родителю, что пользователь хочет записаться или отменить запись.

**Почему передаём обработчик, а не пишем запрос прямо в каждой карточке?** Карточка отвечает за отображение и выбор действия. Родитель отвечает за запрос и обновление общих данных. Если каждая карточка самостоятельно хранила бы копию расписания и счётчиков, их было бы сложнее согласовать между каталогом, программой и календарём.

**Почему не сделать весь сайт одной функцией?** Повторяемые части пришлось бы копировать, а любое изменение задевало бы большой объём кода. Отдельный компонент позволяет изменить карточку сразу во всех местах её использования. При этом деление не должно быть механическим: отдельная функция для каждой строки HTML обычно не нужна.

## 2. Почему именно эти технологии

### React — управление сложным интерфейсом

В ТФлоу после одного действия меняется несколько вещей: запись на активность влияет на кнопку, свободные места и персональную программу. В React мы меняем состояние, а компоненты описывают, как оно должно выглядеть. Не приходится вручную искать каждую кнопку через `querySelector` и менять её текст.

**Вместо чего:** чистого JavaScript с ручным изменением DOM. Он хорошо подходит небольшим страницам и используется в наших формах авторизации. Для основной части приложения с большим числом связанных состояний компонентная модель удобнее. Vue или Svelte тоже могли бы решить задачу: React не является единственным технически правильным выбором.

### TypeScript — согласованность данных

В [types.ts](../lib/types.ts) описаны `FlowEvent`, `Activity`, `Room`, `Profile`. Если компонент ожидает активность с `room_id`, TypeScript помогает не передать ему мероприятие с другой структурой. Он также проверяет типы props и допустимые значения роли.

**Вместо чего:** обычного JavaScript без статических типов. TypeScript добавляет проверку до запуска и помогает редактору показывать ошибки при изменении структуры данных. Цена — необходимость поддерживать типы. Важно: типы удаляются при сборке и сами не проверяют JSON с сервера. У общего `send` пока есть `Promise<any>` — это место, где проверка слабее, чем могла бы быть.

### Vite — разработка и сборка

[Vite](../vite.config.mts) запускает интерфейс при разработке и собирает TSX, JavaScript и CSS в файлы для браузера. Прокси направляет `/api` и страницы входа к Django, чтобы интерфейс обращался к одному адресу.

**Вместо чего:** ручной настройки сборщика или более сложного конфигурационного набора. Vite даёт нужную основу с небольшой конфигурацией. Next.js решает более широкий набор задач, включая серверный рендер и маршруты; у нас уже есть Django, а основная часть UI работает как клиентское приложение. Поэтому добавлять второй полноценный серверный фреймворк для текущей схемы необязательно.

### Собственный CSS — контроль над нашим интерфейсом

Основное оформление находится в [app/flow.css](../app/flow.css), [app/responsive.css](../app/responsive.css) и стилях отдельных компонентов. Цвета и поверхности задаются в том числе CSS-переменными. Tailwind подключён, но большая часть разметки использует собственные классы.

**Вместо чего:** готовой библиотеки компонентов вроде Material UI или Bootstrap. Такая библиотека быстрее даёт типовые формы и кнопки, но её оформление и поведение пришлось бы подгонять под наш дизайн, флоу и студию. Собственный CSS даёт точный контроль; цена — мы сами отвечаем за отступы, состояния, адаптивность и доступность.

### Fetch — запросы без дополнительной библиотеки

Fetch уже есть в браузере. Наш `send` добавляет адрес API, cookie, JSON и CSRF, затем превращает ошибочный ответ в ошибку приложения.

**Вместо чего:** Axios. Для нынешних запросов встроенного API достаточно. Если потребуются сложные перехватчики, единая стратегия повторов и другие возможности, их нужно будет реализовать или выбрать библиотеку. Fetch сам не считает HTTP 400/500 исключением — поэтому мы явно проверяем `response.ok`.

### Lucide и Golos — единый внешний вид

Lucide даёт SVG-иконки камеры, календаря, поиска и других действий. SVG масштабируется без пикселизации, а цвет можно согласовать с текстом. Это удобнее набора несогласованных PNG или emoji, внешний вид которых отличается между системами.

Golos хранится локально в `public/fonts`. Он поддерживает русскоязычный интерфейс и не требует обращения к стороннему сервису шрифтов. Системный шрифт был бы легче в загрузке, но выглядел бы по-разному на устройствах.

## 3. Компоненты, которые собирают приложение

### `App` — сначала узнать пользователя

Файл: [src/main.tsx](../src/main.tsx).

**Что делает:** при открытии запрашивает `/api/auth/me`, показывает загрузку или ошибку подключения, затем передаёт пользователя в `TFlow`.

**Почему отдельно:** сначала нужно понять, кто открыл сайт, и только затем строить интерфейс участника, организатора или гостя. Если каждый экран самостоятельно определял бы пользователя, появились бы повторные запросы и разные состояния авторизации. Здесь начальный запрос находится в одном месте; при уходе его можно отменить через `AbortController`.

### `TFlow` — связывает экраны и общие данные

Файл: [app/tflow.tsx](../app/tflow.tsx).

**Что делает:** хранит маршрут, данные каталога и профиля, открытый диалог, уведомления об операциях; отправляет общие запросы и обновляет данные после действий. Например, карточка сообщает «записаться», а `TFlow` выполняет запрос и обновляет программу.

**Почему состояние здесь:** события, записи и профиль нужны нескольким экранам. Общий родитель позволяет передавать им согласованные данные. Redux для этого не обязателен. При дальнейшем росте стоило бы выделить загрузчики и API-клиент: нынешний `TFlow` большой, и его размер — недостаток, а не цель архитектуры.

**Почему hash-маршруты:** адрес вида `/#event/123` позволяет открыть конкретное событие без отдельного серверного пути для каждого экрана. React Router дал бы более развитую модель навигации, но добавил бы зависимость. Сейчас маршруты разбираются вручную; цена простоты — ручное сопровождение и отсутствие серверного React-рендера.

### `EventPage` — разделяет информацию о событии

Файл: [event-page.tsx](../app/ui/event-page.tsx).

**Что делает:** показывает вкладки «Событие», «Программа», «Моя программа». Последняя доступна вошедшему участнику. Содержимое получает через props, а выбранную вкладку хранит локально.

**Почему вкладки:** описание и большая программа не образуют один бесконечный экран. **Почему компонент получает готовые части интерфейса:** он управляет переключением, а не обязан знать, как записывать участника или строить флоу. Вкладки имеют роли и клавиатурное управление; просто три кликабельных `div` не дали бы этого поведения.

### `OrganizerManage` — рабочее пространство организатора

Файл: [organizer-manage.tsx](../app/ui/organizer-manage.tsx).

**Что делает:** объединяет сведения о своём событии, программу, аудитории, участников и действия управления. Использует специализированные дочерние компоненты, вместо того чтобы заново реализовывать календарь и формы внутри себя.

**Почему отдельный экран:** задачи организатора отличаются от просмотра события участником. Ему нужны редактирование и управление, а участнику — информация и запись. Разделение уменьшает количество лишних элементов. Проверку права владельца всё равно делает сервер: отдельный экран сам по себе не защищает данные.

## 4. Компоненты программы и времени

### `ActivityCard` — один пункт программы

Файл: [activity-program.tsx](../app/ui/activity-program.tsx).

**Что делает:** показывает время, аудиторию, спикера, описание и места. Выбирает нужное действие: записаться, отменить запись, встать в очередь или выйти из неё. Через `activityAvailability` проверяет начало, заполненность и пересечение с персональной программой.

**Почему общая карточка:** один пункт может появляться в программе события и личной программе. Общая логика не позволяет в одном месте случайно разрешить запись, а в другом — запретить по другой формуле. Отдельные карточки могли бы отличаться оформлением, но основные правила стоило бы всё равно разделять через общую функцию.

### `ActivityProgram` — список и фильтры активностей

Тот же файл: [activity-program.tsx](../app/ui/activity-program.tsx).

**Что делает:** хранит локальные фильтры по тексту, аудитории, дню и доступности, отбирает активности и передаёт их представлению программы.

**Почему фильтры здесь, а не в `ActivityCard`:** фильтр определяет состав всего списка. Одна карточка не должна знать о том, какие соседние карточки скрыты. **Почему не запрос на сервер при каждом символе:** программа уже загружена и обычно невелика. Для очень большой программы серверный поиск и постраничная загрузка были бы уместнее.

### `EventFlows` — раздел флоу внутри мероприятия

Файл: [event-flows.tsx](../app/ui/event-flows.tsx).

**Что делает:** добавляет заголовок и действия раздела, подключает вертикальную программу. Если активностей ещё нет, объясняет пустое состояние и может показать временные рамки самого мероприятия.

**Почему отдельная обёртка:** флоу имеет собственный контекст, но использует ту же программу. Не нужно копировать фильтры и правила записи ради другой точки входа.

### `FlowSchedule` — визуальная шкала времени

Файл: [flow-schedule.tsx](../app/ui/flow-schedule.tsx). Расчёты: [flow-layout.ts](../lib/flow-layout.ts), [readable-flow.ts](../lib/readable-flow.ts).

**Что делает:** переводит время в вертикальные координаты; параллельные активности располагает рядом. Показывает весь интервал мероприятия, масштаб, цвета и красную линию текущего времени.

Например, лекция 10:00–11:00 и практикум 10:30–11:30 должны частично стоять рядом. Обычный список показал бы порядок, но хуже объяснил бы одновременность. Длительность задаёт базовую высоту, а дополнительная обработка делает короткие блоки читаемыми.

**Почему собственная раскладка, а не готовый календарь:** нам нужны конкретные правила коротких блоков, диапазон мероприятия, персональные действия и оформление. Готовая библиотека могла бы дать часть возможностей быстрее, но потребовала бы адаптации. Цена собственного решения — сложную геометрию и мобильную прокрутку проверяем сами.

**Почему расчёты в `lib`:** функцию размещения можно проверить массивом интервалов без браузера. JSX отвечает за отображение, функция — за координаты. Это проще сопровождать, чем смешать алгоритм и HTML.

### `ProgramTimeline` и `useTimelineEditor` — визуальное редактирование

Файлы: [program-timeline.tsx](../app/ui/program-timeline.tsx), [use-timeline-editor.ts](../app/ui/use-timeline-editor.ts), [program-editing.ts](../lib/program-editing.ts).

**Что делают:** дают организатору временное представление по аудиториям и обработку перемещения/изменения границ. Положение указателя преобразуется во время с нужным шагом и ограничением рамками мероприятия.

**Почему hook отдельно от компонента:** жесты, промежуточный диапазон и обработчики указателя — самостоятельная логика. Её не обязательно держать вперемешку с разметкой шкалы. **Почему не только drag-and-drop:** на телефоне и при точной установке времени удобнее поля ввода, поэтому визуальное управление дополняется формой.

### `useProgramMontage` и `TimelineMenu` — операции над программой

Файлы: `app/ui/use-program-montage.ts`, `app/ui/timeline-menu.tsx`.

**Что делают:** hook хранит буфер копирования/вырезания, занятость, ошибки и токены отмены серверных операций. Меню показывает действия над выбранным пунктом. Перед вставкой проверяется, что исходная активность не изменилась после копирования.

**Почему не просто скопировать объект в массиве React:** нужно сохранить изменение в базе, учесть связанные записи и уметь корректно отменить действие. Локального массива недостаточно. Меню и клавиатурные команды дополняют перетаскивание: сложные операции не приходится выражать только жестами.

### `ProgramGraphEditor` и `ActivityForm` — быстрое и подробное изменение

Файлы: [program-graph-editor.tsx](../app/ui/program-graph-editor.tsx), [program-item-form.tsx](../app/ui/program-item-form.tsx).

**Что делают:** `ProgramGraphEditor` редактирует основные параметры рядом с графиком и сообщает ему диапазон предпросмотра. `ActivityForm` даёт подробную форму активности, включая описание и дополнительные параметры.

**Почему два представления:** для быстрого сдвига времени не обязательно открывать все поля, а для подготовки содержания нужна полная форма. Удалить подробную форму в пользу одних жестов означало бы ухудшить точность и доступность. Проверки конца после начала и границ события выполняются клиентом для обратной связи, затем сервером для сохранения.

### `ProgramSwap` — обмен с объяснением последствий

Файл: [program-swap.tsx](../app/ui/program-swap.tsx).

**Что делает:** получает серверный предпросмотр обмена пунктов и показывает «было → будет», затем отправляет подтверждение с ожидаемой версией события.

**Почему не просто поменять два времени в браузере:** обмен может затронуть промежуточные активности и записи участников. Только сервер знает актуальные данные. Версия `expected_event_updated_at` позволяет обнаружить, что другой организатор уже изменил программу, вместо молчаливой перезаписи его работы.

### `Calendar` — личное расписание

Файлы: [calendar.tsx](../app/ui/calendar.tsx), [lib/calendar.ts](../lib/calendar.ts).

**Что делает:** собирает билеты, выбранные активности и собственные мероприятия; показывает месяц и день. Учитывает пересечения и события через полночь.

**Почему отдельно от флоу:** флоу объясняет программу одного мероприятия, календарь — личное время пользователя между разными событиями. Внешний Google Calendar мог бы дополнять это, но не знает наших состояний записи, мест и очереди. Экспорт `.ics` позволяет перенести снимок расписания во внешний календарь без полной интеграции.

**Почему время вынесено в `time.ts`:** одно и то же событие должно показываться одинаково в карточке, календаре и редакторе. Общие функции явно используют МСК; обычный `new Date(...).toLocaleString()` без зоны зависел бы от настроек компьютера.

## 5. Формы и повторяемые элементы

### `Modal` — общий диалог

Файл: [dialog.tsx](../app/ui/dialog.tsx).

**Что делает:** показывает содержимое через нативный `<dialog>`, блокирует прокрутку страницы, возвращает фокус после закрытия. Учитывает Escape, фон и запрет случайного закрытия во время операции.

**Почему `<dialog>`, а не просто блок поверх страницы:** браузер предоставляет модальный режим и базовое управление фокусом. Для собственного `div` пришлось бы отдельно реализовать клавиатурное поведение и изоляцию фона. Готовая библиотека тоже подошла бы, но здесь используется возможность платформы без ещё одной UI-зависимости.

### `QuickEventForm` — создание и изменение события

Файл: [quick-event-form.tsx](../app/ui/quick-event-form.tsx).

**Что делает:** делит ввод на шаги, проверяет текущие поля, учитывает очный/онлайн-формат; поддерживает сценарии изменения и переноса. При сдвиге начала может сдвигать конец на ту же величину, сохраняя длительность.

**Почему шаги:** большая форма особенно тяжела на телефоне. Разделение уменьшает число одновременно видимых решений. Одна длинная форма позволила бы быстрее просмотреть всё сразу, но занимала бы больше места; поэтому выбор зависит от сложности сценария.

### `useSubmit`, `FormError`, `Submit` — повторяющееся поведение форм

Файл: [forms.tsx](../app/ui/forms.tsx).

**Что делают:** `useSubmit` собирает `FormData`, включает `busy`, ловит ошибку и снимает занятость в `finally`. `FormError` одинаково показывает ошибку, `Submit` — состояние кнопки сохранения.

**Почему не копировать это в каждую форму:** легко забыть снять загрузку после исключения или показать ошибку разными способами. **Почему не React Hook Form/Formik:** нынешние формы в основном можно обработать нативными средствами. При значительно более сложных связанных полях и валидации специализированная библиотека могла бы упростить код.

### `CategorySelect` — одна категория с поиском

Файл: [category-select.tsx](../app/ui/category-select.tsx).

**Что делает:** показывает компактное поле и ограниченный список подсказок. Запрос ищет по всему справочнику, выбор сохраняет одну категорию. Поддерживает клавиатуру и касания; скрытый `select` обеспечивает значение для формы.

**Почему не обычный огромный `<select>`:** в нём трудно искать тему, а нативное раскрытие занимает слишком много места. **Почему не свободный текст:** «ИИ», «ai» и «искусственный интеллект» не должны создавать разные категории. Поиск помогает выбрать согласованное значение, а не порождать новый справочник.

### `InterestPicker` — несколько интересов

Файл: [interest-picker.tsx](../app/ui/interest-picker.tsx).

**Что делает:** ищет темы, добавляет выбранные интересы тегами и позволяет удалять их. Использует тот же справочник, что категории.

**Почему отдельно от `CategorySelect`:** там выбирается одно значение, здесь — набор. Состояния, подписи и отправка формы отличаются. Большой набор чекбоксов показал бы всё сразу, но перегрузил бы страницу и телефон. Поиск плюс видимые теги компактнее и показывает уже сделанный выбор.

### `CityPicker` — подсказки города

Файл: [city-picker.tsx](../app/ui/city-picker.tsx).

**Что делает:** помогает ввести город через подсказки и передать значение форме.

**Почему подсказки, а не длинный список или геолокация:** ввод быстрее сужает список. Геолокация требует разрешения и показывает текущее положение, хотя пользователь может искать событие в другом городе. Она могла бы быть дополнительным удобством, но не должна заменять ручной выбор.

### Компоненты профиля

Файл: [profile-data.tsx](../app/ui/profile-data.tsx).

- **`ExpandedProfileForm`** редактирует общий профиль. Большинство полей необязательно, почта аккаунта показана отдельно только для чтения. Общая форма позволяет заполнить данные один раз.
- **`CompleteRegistrationForm`** собирает недостающие данные при конкретной записи. Отдельный компонент нужен, потому что требования мероприятия отличаются от правил общего профиля; заставлять всех заранее заполнять все возможные поля неудобно.
- **`ParticipantDetails`** одинаково показывает поля участника. Это предотвращает разное представление одной информации в профиле и организаторских экранах.

### `Avatar`, `AvatarForm`, `AccountMenu`, `BrandLogo`

Файлы: [avatar.tsx](../app/ui/avatar.tsx), [account-menu.tsx](../app/ui/account-menu.tsx), [brand-logo.tsx](../app/ui/brand-logo.tsx).

`Avatar` показывает изображение или замену при его отсутствии, а `AvatarForm` отвечает за загрузку/удаление. Разделение позволяет использовать аватар в шапке, не подключая к каждому экземпляру всю форму. `AccountMenu` объединяет действия аккаунта в компактном меню вместо ряда постоянных кнопок. `BrandLogo` централизует отображение фирменного знака и выбор варианта для темы.

### `EventArt` — оформление обложки

Файл: [event-card.tsx](../app/ui/event-card.tsx).

**Что делает:** строит декоративную обложку из CSS-форм или варианта изображения. Его использует, в частности, карточка организатора в `TFlow`.

**Почему CSS-формы:** они не требуют отдельной фотографии для каждого нового события, легко перекрашиваются и масштабируются. Настоящее изображение лучше передавало бы содержание события, но потребовало бы подбора/загрузки и обработки. Декоративная обложка не заменяет текст названия.

## 6. Регистрация, клубы и уведомления

### `EventRegistrationAction` и `EventWaitlists`

Файл: [event-waitlist.tsx](../app/ui/event-waitlist.tsx).

**Что делают:** показывают подходящее действие регистрации и состояние очереди на мероприятие.

**Почему отдельные компоненты:** «записан», «нет мест», «в очереди» — разные состояния с разными действиями. Явная логика уменьшает риск показать две противоречащие кнопки. Очередь полезнее одного отказа «мест нет»: участник может получить освободившееся место. Продвижение выполняет сервер, а компонент отражает результат.

### `Clubs` — поиск сообщества по интересам

Файл: [clubs.tsx](../app/ui/clubs.tsx).

**Что делает:** объединяет поиск, категорию, клубы, вступление и управление доступными действиями.

**Почему отдельная сущность, а не тег мероприятия:** клуб существует между событиями, имеет участников и подписки. Тег только классифицирует событие и не описывает такое постоянное объединение людей.

### `NotificationCenter` и `CheckInStatus`

Файлы: [notification-center.tsx](../app/ui/notification-center.tsx), [check-in-status.tsx](../app/ui/check-in-status.tsx).

`NotificationCenter` показывает историю, непрочитанное и отметку прочтения; страницы загружаются по курсору. Это нужно вместо одних исчезающих сообщений: важное изменение можно найти позже, не загружая весь архив сразу. Краткий toast в `TFlow` остаётся обратной связью на действие.

`CheckInStatus` показывает факт подтверждённого входа. Это отличается от регистрации: зарегистрироваться можно заранее, а посещение подтверждается отдельно. Смешивать эти статусы означало бы выдавать всех записавшихся за пришедших.

### `PushSettings` и `useNotificationUpdates` — доставка и обновление сообщений

Файлы: `app/ui/push-settings.tsx`, `app/ui/use-notification-updates.ts`.

`PushSettings` по явному нажатию запрашивает разрешение, регистрирует service worker и сохраняет подписку через API. Push позволяет получать сообщение и без открытой вкладки; обычный React-компонент после закрытия страницы уже не работает. Для доставки нужны также настроенный сервер и поддержка устройства, а наличие service worker само по себе не означает полноценную офлайн-работу сайта.

`useNotificationUpdates` обновляет краткую сводку уведомлений раз в пять секунд при видимой странице, при фокусе и при сообщении от service worker. **Почему отдельная сводка:** ради нового счётчика не обязательно каждый раз загружать весь каталог. Push отвечает за доставку вне страницы, а история на сайте остаётся доступна независимо от разрешения push.

### `ReleaseUpdate` — предложение обновить приложение

Файл: `app/ui/release-update.tsx`.

**Что делает:** сравнивает идентификатор загруженной сборки с серверным и сообщает, что доступна новая версия.

**Почему не перезагружать автоматически:** организатор может в этот момент редактировать программу. Компонент предлагает сначала сохранить изменения и только затем обновить страницу. Обычная кнопка перезагрузки не подсказала бы пользователю, что сервер уже обновлён.

## 7. QR и видео: почему используем библиотеки

### `QRScanner` и ZXing — распознавание пропуска

Файл: [qr-scanner.tsx](../app/ui/qr-scanner.tsx).

**Что делает:** даёт выбрать событие, включить камеру или загрузить QR; декодирует код и отправляет результат на проверку входа. При закрытии останавливает камеру, ограничивает повторную обработку одного кода.

**Почему ZXing:** декодирование QR включает обработку изображения, поиск кода и исправление ошибок. Писать это самостоятельно ради пропуска нецелесообразно. Нативный `BarcodeDetector` мог бы уменьшить зависимость, но рассчитывать на одинаковую поддержку во всех нужных браузерах нельзя; перед выбором потребовалась бы проверка целевых устройств.

**Почему одного QR недостаточно:** распознать строку и разрешить вход — разные задачи. Django проверяет организатора, регистрацию и повторный вход для конкретного события. Клиент не может достоверно заменить эту проверку своей надписью «успех».

### `Webinar` и LiveKit — интерактивные медиа

Файл: [webinar.tsx](../app/ui/webinar.tsx).

**Что делает:** получает статус и доступ к эфиру, подключает комнату LiveKit, отображает медиатреки и управляет устройствами/состоянием подключения.

**Почему LiveKit, а не свой WebRTC с нуля:** одного вызова камеры недостаточно. Нужны сигналинг, комнаты, передача треков, переподключение и разрешения публикации. Библиотека и медиасервер дают готовую основу. Цена — зависимость от инфраструктуры и библиотеки.

**Почему не просто встроить ссылку на стороннюю встречу:** так можно было бы быстрее получить видеосвязь, но пользователь переходил бы в другой сервис, а связь эфира с регистрацией и активностью программы была бы слабее. Наша студия встроена в сценарий события. Это не отменяет необходимости правильно настроить сервер.

### `HttpWebinar`, `BroadcastCapture`, `BroadcastUpload`, HLS

Файлы: [http-webinar.tsx](../app/ui/http-webinar.tsx), [http-broadcast.ts](../lib/http-broadcast.ts).

**Что делают:** `BroadcastCapture` собирает камеру/экран и звук, `BroadcastUpload` отправляет записанные браузером фрагменты, серверный FFmpeg делает HLS, а `HttpWebinar` воспроизводит трансляцию и показывает её состояние/чат.

**Почему есть второй режим:** WebRTC зависит от медиасервера и сетевых маршрутов. HTTP-трансляция позволяет использовать обычный HTTPS приложения без отдельных публичных медиапортов. Но ей всё равно нужен постоянный обработчик видео на сервере.

**Почему `hls.js`, а не только `<video src>`:** не каждый браузер воспроизводит HLS одним нативным `src`. Библиотека работает с поддерживаемыми браузерными медиа-API; при наличии встроенного HLS предусмотрен нативный путь.

**Чем платим:** сегменты и буфер дают задержку, сервер тратит ресурсы на кодирование. Это режим «ведущий → зрители», его нельзя выдавать за равноценную многопользовательскую WebRTC-встречу. Транспорт выбирается конфигурацией сервера, а не автоматически заменяется при любой ошибке сети.

### `WebinarChannels`, `AccessKeyManager` и `KeyAccessPage`

Файлы: [webinar-channels.tsx](../app/ui/webinar-channels.tsx), `app/ui/access-keys.tsx`.

`WebinarChannels` помогает выбрать отдельный онлайн-флоу или общий эфир мероприятия. Это нужно, потому что одновременно могут идти разные активности, у которых не должны смешиваться звук и чат.

`AccessKeyManager` позволяет организатору выдать или отозвать ключ помощника для сканирования. `KeyAccessPage` после входа в аккаунт проверяет ключ/приглашение и открывает разрешённый сканер или эфир конкретной активности. Это удобнее выдачи помощнику полного кабинета организатора: разрешение ограничено задачей и проверяется сервером.

**Почему видеокомпонент загружается через `lazy`:** медиабиблиотеки крупные, а большинство посетителей сначала открывает каталог. Динамический импорт откладывает загрузку до входа в нужный раздел; `Suspense` показывает состояние ожидания. Статический импорт был бы проще, но увеличил бы объём сразу необходимого кода.

## 8. React hooks на примерах нашего проекта

### `useState` — то, что пользователь должен увидеть

Пример: выбранная категория, вкладка `EventPage`, ошибка формы. Изменение состояния просит React повторно отобразить компонент. Обычная локальная переменная сбрасывалась бы при новом вызове компонента и не сообщала бы React, что интерфейс нужно обновить.

### `useRef` — объект или значение между рендерами

Пример: ссылка на `<video>`, экземпляр комнаты, номер актуального запроса, блокировка сканирования. Изменение `ref.current` не вызывает рендер. Это подходит служебным данным, но не заменяет state для видимого статуса кнопки.

### `useEffect` — работа с внешним миром

Пример: запрос данных, таймер обновления, `hashchange`, подключение к медиа. Возвращаемая функция очищает ресурсы. Если запускать таймер прямо в теле компонента, он мог бы создаваться при каждом рендере и оставлять несколько одновременно работающих копий.

### `useMemo` и `useCallback` — повторное использование

`useMemo` сохраняет результат вычисления, пока зависимости не изменились; используется, например, для раскладки флоу. `useCallback` сохраняет ссылку на функцию, например общий `send`, который передаётся компонентам и используется в эффектах.

Это не обязательная обёртка для каждой строки кода. Мемоизация нужна там, где важна стоимость пересчёта или стабильность ссылки, и сама имеет сложность сопровождения. Она не отменяет правильный список зависимостей.

### `useId` и `useSyncExternalStore`

`useId` связывает поле, подсказку или вкладку с уникальным идентификатором. Фиксированный ID мог бы повториться при нескольких экземплярах компонента.

`useSyncExternalStore` в [use-theme.ts](../lib/use-theme.ts) подписывает React на тему, которую меняет общий скрипт страницы. Это внешний источник состояния, используемый также вне React на страницах авторизации. Поэтому не нужно хранить несогласованные копии темы отдельно в каждом компоненте.

## 9. Общие решения, которые объясняют многие компоненты

**Почему передаём данные сверху вниз.** Родитель хранит общую программу и передаёт её карточкам. Обратное действие идёт обработчиком. Так понятнее, кто владеет данными; глобальный store понадобился бы, если эта схема стала бы слишком сложной.

**Почему есть серверное обновление после операции.** Запись может изменить места, очередь и расписание. Вместо ручного угадывания всех последствий фронтенд перечитывает серверные данные. Это проще для согласованности, но добавляет запрос и ожидание.

**Почему polling, а не WebSocket для обычных обновлений.** Периодические HTTP-запросы проще текущей инфраструктуре. Цена — задержка и дополнительные обращения. WebSocket/SSE подошли бы для более частых обновлений после оценки нагрузки; для отправки видео нужен отдельный медиатранспорт, не просто замена polling.

**Почему нативные HTML-поля.** Они уже умеют ввод, фокус, отправку форм и базовую проверку. Специальный компонент делаем там, где есть конкретная проблема, как поиск категории. Полностью собственный элемент потребовал бы вручную повторять ещё и доступность.

**Почему CSS-переменные для двух тем.** Компонент использует смысловой цвет текста/поверхности, а тема меняет его значение. Не приходится писать две копии компонента. Скрипт [theme.js](../public/theme.js) применяет тему до запуска React, уменьшая вспышку неправильного оформления.

**Почему Grid и Flexbox для телефона.** Они позволяют перестраивать те же компоненты по доступной ширине: карточки, поля, кнопки и навигацию. Отдельная мобильная версия удвоила бы поддержку. При этом таймлайн со множеством колонок может прокручиваться внутри себя — это осознанная часть визуализации.

**Почему отдельно проверяем сервером.** Пользователь может изменить JavaScript или отправить HTTP-запрос вручную. Ограничение кнопки улучшает удобство, но права владельца, вместимость и конфликты обязан проверять Django. CSRF-токен защищает изменяющие запросы в cookie-схеме, а не заменяет проверку прав.

**Почему Vitest и Testing Library.** Vitest запускает проверки функций и компонентов, Testing Library помогает проверять их через видимые подписи и действия пользователя. Так тест меньше зависит от внутреннего устройства компонента. Но jsdom не подтверждает настоящую геометрию телефона или доступность камеры: для этого нужен браузер и реальные устройства/сервисы.
