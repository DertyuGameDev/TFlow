# Архитектура

Ссылки для сдачи находятся в [README проекта](../../README.md). Аккаунты и сценарии для демонстрации — в [описании фикстур](demo-data.md).

## Компоненты

Основная бизнес-логика — модульный монолит Django. Интерфейс React обращается к JSON API; доступ определяется серверной сессией. В production Django также обслуживает собранный интерфейс и статические ресурсы через WhiteNoise.

```text
Браузер / React
  └─ HTTP(S) → Django views → contracts / services → Django ORM → БД
                    ├─ уведомления → центр сообщений / Web Push worker
                    ├─ HTTPS-видео → фрагменты → FFmpeg worker → приватный HLS
                    └─ LiveKit → подписанный токен → подключение браузера к SFU

Django → метрики → Prometheus → Grafana
Django → JSON-логи → Alloy → Loki → Grafana
Prometheus → Alertmanager → настроенный получатель
```

Локально по умолчанию используется SQLite, серверная конфигурация поддерживает PostgreSQL через `DATABASE_URL`. Вариант VM использует Gunicorn, Caddy и systemd. Фронтенд имеет hash-маршруты; `/#event/<id>` — страница интерфейса, `/api/events/<id>` — API-ресурс.

## Данные

Мероприятие `Event` принадлежит организатору. `Room` описывает очную или онлайн-аудиторию. `Activity` связывает мероприятие, аудиторию, интервал, вместимость и режим записи.

`EventRegistration` — билет мероприятия. `Registration` — отдельная запись на флоу либо календарная отметка открытого флоу. `CheckIn` и `ActivityAttendance` хранят фактическое посещение. Очереди мероприятия и флоу независимы. Членство `Membership` в клубе не заменяет билет.

Видео имеет отдельные модели `Webinar` (LiveKit), `HttpBroadcast` и `BroadcastMessage` (HTTPS). Уведомления хранятся в `Notification`; Web Push использует подписки и задания доставки, напоминания — записи дедупликации. Поля, внешние ключи и ограничения: [ER и словарь](er/README.md).

## Критические операции

Сервисы расписания используют `schedule_write()`: транзакцию и общую строку `ScheduleLock`. На PostgreSQL применяется `select_for_update()`, на SQLite — режим `IMMEDIATE`. После получения блокировки повторно проверяются актуальные места, права и расписание; затем фиксируются записи и соответствующие уведомления.

Общая блокировка обеспечивает простой порядок связанных изменений, но сериализует критические записи. Увеличение количества HTTP-workers не снимает этот предел. Метрики ожидания и удержания блокировки позволяют оценивать стоимость. Новые операции, влияющие на инварианты расписания, должны использовать тот же протокол.

Уникальные ограничения защищают от дублей, CHECK — от недопустимых значений. Проверка принадлежности аудитории событию, календарные конфликты и суммарная вместимость выполняются сервисами; один FK не гарантирует этих правил.

## Временные интервалы и версии

Пересечение определяется условием `a.start < b.end and a.end > b.start`. Конец интервала исключён: соседние занятия разрешены. Проверяется занятость аудитории и личное расписание участника, включая разные мероприятия.

Для изменения флоу клиент может передать `expected_updated_at`. Несовпадение возвращает `STALE_ACTIVITY`; проверка версии дополняет, а не заменяет блокировку. Предложения альтернатив не резервируют ресурсы: при сохранении проверка повторяется.

API передаёт даты как Unix timestamp в миллисекундах. Django использует timezone-aware даты; интерфейс показывает расписание по Москве. Расчёты календаря находятся в `lib/time.ts` и `lib/calendar.ts`.

## Границы системы

Внешние вызовы и транзакция БД не образуют распределённую транзакцию. Отказы медиа- и push-провайдеров обрабатываются отдельно. Для Web Push предусмотрены ограниченные повторные попытки; при отмене регистрации доступ отзывается независимо от успешности внешнего отключения зрителя.

Метрики и логи локального контура не доказывают наблюдаемость production. Состояние служб и источников данных проверяется при установке в конкретное окружение.

## Публикация и мониторинг

GitHub `main` проходит проверки, затем изменения переносятся через MR в GitLab `master`. После GitLab CI задача `deploy-spirit-cu` устанавливает тот же проверенный релиз на VM. Его идентификатор доступен через `/api/version`.

На VM Grafana и Prometheus запускаются отдельными systemd-службами и слушают loopback. `/grafana/` проксируется Django после проверки сессии и списка разрешённых организаторов. Grafana работает от технического Viewer; изменять конфигурацию через этот прокси нельзя. Дашборд показывает доступность API, HTTP-нагрузку, ошибки, задержки и ожидание блокировки расписания. Prometheus опрашивает защищённый Bearer-токеном `/internal/metrics`; метрики Gunicorn workers объединяются через multiprocess-каталог. Полный локальный контур с Loki/Alloy описан отдельно и не подменяется показом пустых источников на production-дашборде.
