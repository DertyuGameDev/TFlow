# Проверки проекта

Из папки `tflow`, после `npm ci` и `npm run setup`:

```sh
npm test                 # Все клиентские и серверные тесты
npm run test:frontend    # Логика клиента и сценарии интерфейса
npm run test:ui          # Только Vitest / Testing Library
npm run test:backend     # Django, отдельная тестовая база
npm run check           # TypeScript, включая код тестов
npm run build           # Проверка production-сборки
```

Новые зависимости тестирования устанавливаются только для разработки. Для тестов не нужны камера, физический микрофон, SMTP и запущенный LiveKit.

## Что добавлено

- Два шага создания события, обязательные поля, онлайн/гибридный формат, сохранение площадки при переключении форматов, перенос с сохранением длительности, ошибки сети и повторная отправка.
- Безопасный отказ от удаления/отмены, блокировка повторного запроса и закрытия во время операции, повтор после ошибки, клик по фону и возврат фокуса.
- Страницы уведомлений без дублей, фильтр непрочитанных, запоздалые ответы, переход после сохранения прочтения, удалённое событие и восстановление после сетевой ошибки.
- Дополнение обязательных полей анкеты без потери уже введённых значений, ошибки конкретного поля и изменение требований организатором.
- Превью пяти участников, открытие и закрытие анкеты с возвратом фокуса, отмена записи, пустой список, переход ко всем участникам и поиск. На странице события анкеты загружаются только владельцу; гости, участники и другие организаторы их не получают.
- Клавиатурный выбор города, сокращения, нормализация старого значения, произвольный город, очистка и заблокированное поле.
- Вход в вебинар без автоматического доступа к устройствам, события речи, выключение и отказ микрофона, ошибка смены устройства, отключение комнаты при выходе.
- Системная/ручная тема, запрет хранилища, синхронизация вкладок, подписи переключателя и контрастный логотип приложения и страницы входа.
- Реальные обработчики запросов LiveKit: подпись серверного токена, адрес и тело запросов, таймауты, ошибки HTTP/JSON, повтор завершения, откат удаления, отзыв билета при сбое видео и смена формата после завершения.
- Команда отправки писем: лимит, отсутствие дублей, неверная настройка, отказ почтового backend, непрерывный режим и завершение по Ctrl+C. Письма остаются в тестовом хранилище Django.
- Письма об изменении события клуба отправляются записанным участникам, а не всем членам клуба. Сохранение активности и перенос без изменений, а также повтор уже выполненного изменения не создают лишних писем.
- Меню аватара: открытие, повторное нажатие, клавиатура, возврат фокуса, закрытие снаружи и POST-форма выхода с CSRF. Состояния событий проверяются на границе окончания, для черновиков и при фильтрации/сбросе в каталоге.
- Подписка клуба: вступление, отключение, повторное вступление, права и CSRF, уведомление только активным подписчикам при первой публикации, отсутствие дублей и откат при сбое очереди. Почтовая проверка использует только хранилище в памяти.
- Создание аудитории вместе с пунктом программы: один запрос, сохранение имени и вместимости, выбор существующей, редактирование, проверка владельца и откат при неверных датах или лимите мест.
- Swagger: публичная схема, разрешение всех ссылок, уникальность операций, актуальные поля форм, CSRF страницы и разрешённые локальные ресурсы.

## Границы автоматических проверок

Делегирование ключами: права владельца, разные ключи на разные онлайн-флоу, запрет смешивания QR и ведения вебинара, хеширование секретов, срок действия, перевыпуск/отзыв, неизменность роли и запрет управления чужим событием. API-тесты проверяют одноразовый вход, минимальный состав ответа сканера, аудит доверенного лица, конкуренцию сканов владельца и помощника, JWT ведущего и принудительное отключение при отзыве без остановки соседнего флоу. Интерфейсные проверки охватывают создание и отзыв, ввод ключа, отдельный POST-транспорт и закрытие делегированной студии.

Параллельные онлайн-флоу: создание разных виртуальных аудиторий на одно время, конфликты одной аудитории и личного расписания, независимые LiveKit-комнаты и JWT, проверка регистрации на конкретную активность, отдельные start/end/restart, отзыв доступа при отмене, завершение всех эфиров при удалении события и откат при отказе медиасервера. Конкурентные запросы проверяют одновременный запуск разных флоу и идемпотентность повторного запуска одного. Интерфейс проверяет выбор потока, прямые ссылки, создание аудитории вместе с активностью, раздельные подключения/чаты и завершение одного подключения без отключения второго.

Очередь мероприятий проверяется отдельно от очереди активностей: FIFO, личная позиция, выход и повторное вступление, увеличение вместимости, заполнение анкеты после изменения требований, пропуск неактивного аккаунта, запрет обхода через регистрацию активности, закрытые события, права и CSRF, откат при ошибке очереди писем. Конкурентные проверки воспроизводят отмену одновременно с новой записью, повторное вступление и распределение одного свободного места. Интерфейсные тесты проверяют недостающие данные, получение билета во время запроса, обновление профиля и выход из устаревшего экрана после получения места. Почта проверяется только в памяти.

Testing Library запускает реальные компоненты в jsdom и взаимодействует с полями и кнопками. В тестах комнаты LiveKit заменяется моделью событий; это проверяет состояние интерфейса и обработку ошибок, а не работу физических устройств. Серверные тесты транспортного слоя подменяют только HTTP-вызов к медиасерверу. Проверки реального потока с двумя браузерами и синтетическим звуком описаны отдельно в `verification.md`.

Для дополнительного отчёта строк покрытия сервера можно установить `coverage` в виртуальное окружение и выполнить:

```sh
.venv/bin/python -m pip install coverage
COVERAGE_FILE=/tmp/tflow.coverage .venv/bin/python -m coverage run --source=backend/flow --omit='*/migrations/*,*/tests/*' backend/manage.py test flow.tests --noinput
COVERAGE_FILE=/tmp/tflow.coverage .venv/bin/python -m coverage report
```

Не запускайте сборку одновременно с серверными тестами: Django читает ресурсы из `dist`, а Vite при сборке заменяет эту папку.

## Воспроизводимая демонстрация

Из `tflow`, на отдельной локальной базе:

```sh
TFLOW_DATABASE_PATH=/tmp/tflow-demo.sqlite3 .venv/bin/python backend/manage.py migrate --noinput
TFLOW_DATABASE_PATH=/tmp/tflow-demo.sqlite3 .venv/bin/python backend/manage.py seed_demo
TFLOW_DATABASE_PATH=/tmp/tflow-demo.sqlite3 NOTIFICATION_EMAIL_ENABLED=0 npm run dev
```

Сначала остановите прежний dev-сервер на тех же портах. Аккаунты: `organizer@demo.example.test` и `participant@demo.example.test`, пароль `Demo-flow-2026!`.
Команда не очищает базу, повторный запуск не дублирует записи, в production запрещён. Создаются событие и два параллельных онлайн-флоу в разных аудиториях. Участником запишитесь на событие/флоу, организатором выдайте QR-ключ и отдельные ключи ведущих в управлении событием.

## Автоматизация

GitHub Actions (`.github/workflows/ci.yml`) при push/PR проверяет типы, клиентские и серверные тесты, миграции, сборку и формирует артефакт релиза.
GitLab CI дополнительно проверяет PostgreSQL и автоматически запускает существующий `deploy_vm` после успешных проверок основной ветки, если настроены защищённые FILE-переменные `TFLOW_VM_SSH_KEY` и `TFLOW_VM_KNOWN_HOSTS`. Остальные параметры — в `deploy/spirit/README.md`.
Без серверных переменных развёртывание пропускается. Секреты команда настраивает в CI, не в репозитории.
