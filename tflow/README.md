# ТФлоу 0.3: Django + React

## Разработка

```bash
npm ci
npm run setup
npm run dev
```

`setup` создаёт `.venv`, устанавливает зафиксированные Python-зависимости и применяет миграции без демо-наполнения и автоматического импорта. `dev` запускает Django на 8000 и Vite на 5173. Node используется для разработки/сборки frontend; все API, доступ и бизнес-операции выполняются в Django.

Данные: `backend/data/tflow.sqlite3` (игнорируется Git). Для аккаунтов используйте обычную регистрацию или управление паролями Django. Демо-аккаунты и шаблонные события удалены.

Для демонстрации `npm run dev` включает `TFLOW_DEMO_MODE=1`: можно зарегистрироваться с коротким именем, без фамилии и с простым паролем, например `1` (подтверждение должно совпадать). Интересы необязательны и свёрнуты. `TFLOW_DEMO_MODE=0 npm run dev` возвращает обычные требования к паролям. На Vercel и при `DJANGO_DEBUG=0` упрощение паролей не действует. Проверки email, прав доступа и расписания сохраняются.

В календаре доступны регистрации, личные активности, лист ожидания и экспорт в `.ics`. В программе события есть поиск, фильтры по дню/аудитории и предупреждения о пересечениях. Очередь автоматически заполняет освободившиеся места с уведомлением; вступление регистрирует пользователя на событие. В профиле нажмите «Изменить фото», чтобы загрузить или удалить аватарку (JPG/PNG/WebP, до 5 МБ и 16 Мп).

Светлая и тёмная темы переключаются кнопкой солнца/луны в шапке и на странице входа. При первом открытии используется тема устройства; ручной выбор сохраняется в браузере и применяется также к регистрации.

Ручной импорт внешнего экспортированного SQLite:

```bash
.venv/bin/python backend/manage.py import_d1 /absolute/path/to/old.sqlite
```

Скрипт работает со снимком, не изменяет исходный файл, не перезаписывает существующие строки и проверяет согласованность расписания перед фиксацией транзакции. Экспорт live D1 не выполняется автоматически.

## Production

Вход ограничен общими для всех процессов счётчиками в БД: за 5 минут не более 10 попыток на пару email/IP и 50 с одного IP; регистрация — не более 10 запросов с одного IP. При превышении возвращается 429 с `Retry-After`. Счётчики не содержат исходные email и IP, истёкшие записи удаляются автоматически. Перед запуском нового релиза требуется обычный `migrate`.

Для собственного reverse proxy настройте `DJANGO_TRUSTED_PROXY_IPS` точными адресами или сетями доверенных прокси. Для Caddy на той же VM: `127.0.0.1/32,::1/128`. Без этого заголовки IP от клиента игнорируются; запросы за прокси учитываются по его адресу. В Vercel используется перезаписываемый платформой `x-vercel-forwarded-for`. Нельзя доверять произвольным клиентским `X-Forwarded-For`.

JSON API принимает тело до 256 КиБ, формы входа и регистрации — до 64 КиБ. Для аватарок общий запрос ограничен 6 МиБ, суммарное содержимое файлов — 5 МиБ с остановкой обработки загрузки до переполнения временного хранилища. Проверки формата и разрешения изображений сохраняются.

Публичный LiveKit должен использовать WSS/HTTPS и секрет подписи не короче 32 байт. Адреса с паролем, query или fragment отклоняются; управляющие запросы не следуют HTTP-перенаправлениям, чтобы не передать bearer-токен другому адресу. Локальный HTTP/WS допускается только при `DEBUG=True`.

Django обслуживает также `dist/index.html`, собранные JS/CSS и страницы входа/регистрации. Node в runtime не нужен. Переменные окружения перечислены в `backend/.env.example`; они передаются окружением процесса/хостинга, файл сам по себе не подгружается.

```bash
npm run build
.venv/bin/python backend/manage.py collectstatic --noinput
# Установить DJANGO_DEBUG=0, DJANGO_SECRET_KEY, DJANGO_ALLOWED_HOSTS и HTTPS proxy settings.
# В корне tflow:
.venv/bin/python backend/entrypoint.py
```

`entrypoint.py` применяет миграции и запускает Gunicorn на порту `PORT` (по умолчанию 8000). Внешний reverse proxy должен предоставлять HTTPS. `DJANGO_TRUST_PROXY=1` допустим только если доверенный proxy перезаписывает `X-Forwarded-Proto`.

SQLite сохраняется в `backend/data`; для нескольких реплик сервера используйте общий PostgreSQL через `DATABASE_URL`. Для SQLite нельзя запускать независимые реплики с отдельными файлами данных и ожидать единого расписания.

### Docker

```bash
docker build -t tflow .
# Передать свои переменные через environment/secret manager:
docker run --env-file /path/to/runtime.env -p 8000:8000 -v tflow-data:/app/backend/data tflow
```

Контейнер не содержит локальную базу, учётные записи, `.env` и секреты. Он работает без root. Dockerfile подготовлен; фактическая сборка Docker не запускалась в текущей среде.

ChatGPT Sites/Cloudflare Worker больше не является runtime этого приложения. Его несекретный манифест сохранён только как `docs/legacy-sites-hosting.json` для исторической публикации. Django опубликован на Vercel: https://tflow-one.vercel.app/. Также поддерживается обычный Python/Docker-хостинг.

### Vercel

Корень проекта: `tflow`, framework: Django, Python 3.12. Задайте `DJANGO_SECRET_KEY` и PostgreSQL `DATABASE_URL` с `sslmode=require` в окружении проекта. Локальная SQLite на Vercel запрещена. Точные домены deployment/production автоматически добавляются в Django allowed hosts и CSRF origins из системных переменных Vercel.

`scripts/build-vercel.py` собирает React с путями `/static/app/` и выполняет только миграции схемы. Vercel собирает статику Django для CDN. Деплой не очищает и не заполняет базу.

Очистка выполняется отдельно и только явно: `.venv/bin/python manage.py reset_data --yes`. Служебная строка блокировки расписания восстанавливается после очистки.

### Профиль и данные при записи

В кабинете события откройте «Данные при записи» и выберите обязательные поля профиля. Имя и почта берутся из аккаунта. Телефон, дата рождения, город, Telegram, работа, должность, образование, сайт, описание и интересы заполняются в профиле или при первой записи, где они нужны.

При записи платформа запрашивает только недостающее и одной транзакцией сохраняет профиль и билет. Проверка действует также для активностей и листов ожидания. Организатор видит переданные данные в карточке участника и при проверке QR; другим посетителям они недоступны. Снимок данных сохраняется на момент записи. Изменение требований не отменяет уже выданные билеты.

## API и новые сценарии

Если на мероприятии закончились места, участник может нажать «Встать в лист ожидания». Позиция видна на странице события, в профиле и в разделе календаря. Очередь не выдаёт билет и доступ по QR или к вебинару до получения места. Выйти можно в любой момент.

Отмена регистрации или увеличение вместимости автоматически передаёт места следующим готовым участникам по порядку вступления. Создаётся обычная регистрация, событие появляется в календаре и приходит уведомление. Неактивные аккаунты и участники без актуальных обязательных полей пропускаются с сохранением очереди; заполнение профиля запускает повторную проверку. После окончания события места не распределяются. Прямой запрос регистрации и запись на активность не позволяют обойти очередь.

API: `POST /api/events/{id}/waitlist` (при необходимости с полями анкеты) и `DELETE /api/events/{id}/waitlist`. Ответ сообщает `waitlisted` и `registered`: если место уже доступно, запись происходит сразу. Поля события `event_waitlisted`, `event_waitlist_position`, `event_waiting_count` показывают личную позицию и общее число ожидающих. Повторные запросы не создают дубли; выдача места, удаление из очереди и уведомление сохраняются одной транзакцией.

Swagger UI доступен по `/api/docs/`, спецификация OpenAPI — `/api/openapi.json`. Документация включает существующие маршруты Django, схемы полей, права и ошибки. CSS и JavaScript Swagger поставляются с Python-зависимостями и обслуживаются самим Django. Войдите в аккаунт на этом сайте: «Try it out» использует его сессию и CSRF-токен. Действия из документации изменяют данные с обычными правами текущего пользователя.

Нажатие на аватар в шапке открывает меню «Профиль» и «Выйти из аккаунта». Выход выполняется POST-запросом с CSRF-защитой.

В каталоге, сохранённых и кабинете организатора есть переключатель «Все / Активные / Завершённые». Активные — опубликованные события, время окончания которых ещё не наступило, включая будущие. Черновики видны владельцу только в состоянии «Все».

Вступление в клуб автоматически включает подписку на новые события, её можно отключить в карточке клуба. Уведомление создаётся при первой публикации встречи. Подробнее — в [описании уведомлений](docs/notifications.md).

При добавлении или редактировании пункта программы выберите существующую аудиторию, «Создать новую аудиторию» или «Создать онлайн-поток». Несколько онлайн-флоу могут идти одновременно в разных аудиториях. Внутри одной аудитории пересечения запрещены. Программа и новая аудитория сохраняются одним запросом: ошибка времени или вместимости откатывает создание обоих объектов. Новую аудиторию затем можно выбирать для остальных пунктов.

Каждая онлайн-активность имеет отдельный вебинар с собственными видео, звуком и чатом. Студия открывается в отдельном окне: обновление основного сайта не прерывает передачу. После обновления самой студии ведущий повторно включает устройства и нажимает «Восстановить трансляцию»; комната и чат сохраняются. Закрытие студии прекращает захват устройств, но не завершает комнату. Эфир завершается явной командой, отзывом доступа или окончанием активности. Для просмотра нужна запись на конкретный флоу; для активности без отдельной регистрации достаточно билета мероприятия. Новые эфиры по HTTPS создаются только для конкретной активности.

HTTP API: `GET/POST /api/activities/{id}/broadcast`, POST принимает `operation: start | resume | end`. Восстановление требует исходного ведущего и секрета публикации из его вкладки, меняет поколение медиа и сохраняет ID комнаты. Начало и восстановление проверяются по текущему расписанию активности на сервере. LiveKit API `/api/activities/{id}/webinar` сохраняется для альтернативного транспорта.

Владелец видит персональные ссылки лекторам в кабинете события. Ссылка открывает только свою активность, требует входа в аккаунт и не меняет роль пользователя. Перенос активности сохраняет ссылку и обновляет её время; отзыв отключает связанную публикацию. В разделе «Сканер QR» организатор сразу получает камеру, а участник вводит токен помощника и сканирует только в пределах этого события. Список участников в кабинете единый: поиск, анкеты и отметки посещения находятся в одном блоке.

### Доступ доверенным лицам

В кабинете своего события на вкладке «Событие» откройте «Доступ доверенным лицам → Управлять ключами». Можно создать QR-ключ для всего мероприятия и отдельный ключ ведущего для каждого онлайн-флоу. Организатор без ключа по-прежнему сканирует только свои мероприятия. Передайте ключ доверенному лицу самостоятельно; оно входит в свой аккаунт, открывает меню аватара → «Доступ по ключу» и вводит ключ.

QR-ключ разрешает только подтверждать вход на конкретное мероприятие: видны имя и результат проверки регистрации, без контактов и анкеты. Ключ ведущего открывает запуск, ведение и завершение одного флоу, без регистрации участником и без доступа к управлению событием. Роли аккаунтов не меняются. Зрители видят трансляцию доверенного ведущего. В отметке входа сохраняются пользователь, выполнивший сканирование, и выданный ключ.

Ключи действуют до окончания мероприятия/флоу. Их можно отозвать или перевыпустить: старый ключ сразу перестаёт выдавать доступ; ведущий отключается только от своей комнаты. При недоступности медиасервера отзыв сохраняется, новые токены не выдаются, клиент отключается при следующей проверке доступа. В базе сохраняются хеши, секрет показывается владельцу только после генерации. Ключи не помещаются в URL и не сохраняются в браузерном хранилище.

API: `GET/POST events/{id}/access-keys` для владельца; `POST access-keys/resolve`, `access-keys/check-in` и `access-keys/webinar` для доверенного пользователя. Авторизация и CSRF обязательны; секрет передаётся полем `key` в JSON. Документация есть в Swagger.

## Активности без отдельной регистрации

В редакторе пункта на графике можно выключить «Нужна отдельная запись». Активность становится доступной всем участникам с билетом на мероприятие. Кнопка «В расписание» создаёт личную календарную отметку без бронирования места и проверки квоты; пересечения личного расписания проверяются. Удаление отметки сохраняет билет и доступ к активности. Без билета API возвращает `EVENT_REGISTRATION_REQUIRED`. Такие пункты можно добавить до их окончания; у обычных активностей запись по-прежнему закрывается к началу.

Поле API `registration_required` по умолчанию равно `true`; отсутствие поля при изменении сохраняет текущий режим. При отключении отдельной записи существующие записи остаются в личном расписании, очередь очищается. Возврат к бронированию отклоняется, если текущих записей больше выбранного лимита. Старые мероприятия сохраняют прежнее поведение после миграции.

Перенос на графике сначала меняет черновик. Галочка или Enter сохраняет новое время, Esc отменяет его. Перетаскивание целого отрезка сохраняет длительность; края изменяют границы. Alt + ←/→ сдвигает на минуту, Shift увеличивает шаг до 15 минут. Обмен доступен прямо в редакторе пункта и показывает изменения перед подтверждением.

## Автоматическая выкладка на Spirit

Основной вход для изменений — GitHub `main`. Workflow `Verify and package` сначала проверяет код, затем задача `sync-gitlab` переносит только новые изменения в GitLab через MR. GitLab повторяет проверки и автоматически запускает `deploy-spirit-cu` после упаковки. GitHub workflow считается завершённым только после успешного деплоя именно этого коммита на VM. Секрет `TFLOW_GITLAB_TOKEN` хранится в GitHub Actions Secrets; в репозитории и аргументах команд его нет.

Синхронизация сохраняет изменения, сделанные непосредственно в GitLab. Базовый GitHub-коммит записывается в служебный trailer `TFLOW-GitHub-Source`, поэтому squash не приводит к повторному переносу старых правок. Конфликт останавливает синхронизацию; принудительный push и автоматический выбор стороны конфликта не используются.

Сайт: https://hack-mmk-25-vm1-162f2c.teleport.t-education.com/#organizer . Для входа требуется авторизация ЦУ. `GET /api/version` показывает идентификатор реально обслуживаемой сборки. Деплой сверяет этот идентификатор, HTML и хеши входных JS/CSS с проверенным артефактом; старый процесс или файл не может пройти проверку только за счёт работающего `/api/health`.

HTML не кэшируется. Открытая вкладка проверяет обновление каждые 30 секунд и при возвращении в неё. Новая версия предлагает кнопку «Обновить»: сначала сохраните форму, чтобы не потерять черновик. Уже открытый JavaScript не заменяется без перезагрузки страницы.
Согласованные сценарии регистрации, посещаемости флоу, очереди, готовые аккаунты и результаты нагрузки: [docs/scenario-improvements.md](docs/scenario-improvements.md).

## Схема базы данных

[ER-схемы: обзор и тематические картинки](docs/er/README.md), [полный словарь полей и ограничений](docs/er/data-dictionary.md).

В кабинете события требования к анкете доступны в верхней вкладке «Что спросить при записи». На графике перенос и изменение краёв сохраняются сразу. Правая кнопка открывает монтаж: вырезать/копировать, разрезать в точке курсора, вставить перед, после или внутрь. Alt + клик разрезает пункт, Shift + перенос на другой пункт меняет их местами. Вставка сдвигает последующие пункты с сохранением длительности. Ctrl/⌘ X, C, V и Z работают, когда фокус на графике; Shift + F10 открывает меню с клавиатуры.

Разрез создаёт самостоятельные активности и сохраняет существующие записи и очередь в обеих частях; дальнейшая запись на них независима. Копия создаётся без записей. Вырезание до вставки не удаляет данные. Последние операции монтажа можно отменять в текущем окне в течение часа; отмена не удалит новую часть, если после операции в ней появились новые записи, посещения или использованный доступ лектора. Пересечения расписания, выход за границы события и изменение активности с незавершённым эфиром отклоняются атомарно.

Локальный набор для жюри: `python manage.py seed_jury` из `backend` (в установленном Python-окружении проекта). Команда добавляет десять участников с логинами `1`…`10` и паролем, совпадающим с логином, а также организатора `test` с паролем `test`. Короткие логины работают только на localhost в DEBUG с установленными фикстурами; адреса аккаунтов — `1@jury.example.test`…`10@jury.example.test` и `test@jury.example.test`. На PostgreSQL и в production команда отказывается выполнять запись. Повторный запуск сохраняет существующие данные и не сбрасывает пароли.

Набор содержит десять опубликованных событий на разных темах, черновик, тридцать активностей, четыре клуба, примеры записей, избранного, очередей и подтверждённых посещений. Одна онлайн-активность идёт в момент первого заполнения. Участник `1` может проверить дозаполнение профиля при записи на событие про дизайн.
