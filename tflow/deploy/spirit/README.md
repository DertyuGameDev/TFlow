# ТФлоу в Spirit

## HTTPS-эфиры без новых сетевых правил

Текущий установщик готовит FFmpeg до переключения приложения, сохраняет
приватную копию app.env и включает `tflow-broadcast.service`. Он не меняет
публичные порты, Caddy или правила Spirit. Обработка работает отдельной
службой под `tflow`, максимум два эфира 960×540/15fps, лимиты 150% CPU и
768 MiB памяти. Временные фрагменты находятся в `/var/lib/tflow/broadcasts`.
`/api/broadcast-health` сообщает только готовность службы; сами видео и чат
требуют аккаунта и регистрации. Передача идёт через рабочий HTTPS-адрес ЦУ.

Во время активного HTTPS-эфира новая выкладка отклоняется до изменения
релиза: сначала нужно завершить эфир и повторить pipeline. Это сохраняет
текущую трансляцию. При сбое запуска нового релиза восстанавливаются прежняя
ссылка приложения и окружение; аддитивная миграция и резервная копия БД
сохраняются. На Vercel постоянный обработчик не запускается.

Тенант: `hack-mmk-25`. Выделенная платформой VM: `vm1`, Ubuntu 24.04,
4 vCPU / 8 ГБ RAM / 50 ГБ диска. Квота команды — одна VM.
DNS: `hack-mmk-25-vm1-162f2c.vm.prodcontest.com`, IP: `158.160.209.13`.

CI в GitLab запускает TypeScript, frontend-тесты, сборку Vite и Django-тесты
с отдельной PostgreSQL 16. После успешных проверок job `package` сохраняет
`release/tflow-release.tar.gz` и `release/manifest.json` с SHA коммита и SHA-256 архива.
Этот архив содержит собранный frontend и Django, без локальных БД и секретов.
Выкладка запускается кнопкой `deploy-spirit` в pipeline ветки `master`;
push сам по себе не перезапускает VM.

## Выкладка из GitLab

После успешных тестов и `package` откройте pipeline `master` и запустите
`deploy-spirit`. Job использует существующий сервисный аккаунт Spirit,
получает текущие SSH-реквизиты только для vm1 и хранит их во временном каталоге
с правами 0700/0600. В логи и артефакты ключи не попадают. Отдельные
`DEPLOY_KEY`, `DEPLOY_HOST`, `DEPLOY_USER` не требуются.

Перед подключением проверяются SHA коммита, SHA-256 релиза, ID VM и SSH host key.
Job обновляет чистый Git checkout на VM только fast-forward, загружает точный
артефакт и запускает установщик. Локальные изменения на VM не перезаписываются.
Повторный запуск того же артефакта не повторяет установку, если manifest совпадает.

После установки проверяются все три службы, внутренний healthcheck, публичный
HTTPS, страница регистрации и отказ в выдаче QR без входа. При ошибке TLS
job завершается **ошибкой**, даже если установка кода на VM прошла.
Он оставлен необязательным ручным шагом, чтобы внешний сетевой сбой не блокировал
проверки кода и слияние. Готовность публикации проверяйте по успешному
`deploy-spirit`, а не только по общему статусу pipeline.

В GitLab создаётся environment `production` со ссылкой на требуемый домен Spirit.

## Временный доступ через ЦУ

После разрешения владельца использовать вход через ЦУ на vm1 включён
Teleport Application Access, порт 8000. Адрес:
https://hack-mmk-25-vm1-162f2c.teleport.t-education.com/.
Платформа приняла настройку и для существующей VM с публичным IP.
Исходный домен VM сохраняется; его сертификат остаётся отдельной задачей.

В pipeline `master` есть ручной job `deploy-spirit-cu`, environment `temporary-cu`.
Он устанавливает тот же проверенный артефакт, добавляет точный адрес gateway
в allowed hosts и CSRF trusted origins, задаёт браузерный URL для QR и ссылок.
Секреты и данные сохраняются; перед изменением env делается приватная копия.
HTTPS redirect, secure cookies и DEBUG остаются с прежними безопасными значениями.

Проверка этого job: внутреннее здоровье приложения, доверенный TLS gateway
и перенаправление на вход через ЦУ. Запросы после входа требуют отдельной
проверки в авторизованном браузере. Само перенаправление на вход не считается
проверкой всей регистрации или камеры.

## Первичная настройка

В интерфейсе Spirit откройте VM и скачайте SSH-ключ. Храните его вне репозитория
с правами `0600`. Пользователь SSH — `ubuntu`, у него доступен `sudo`.
Скопируйте этот каталог на выделенную VM и выполните:

```sh
sudo python3 bootstrap.py hack-mmk-25-vm1-162f2c.vm.prodcontest.com
```

Скрипт устанавливает PostgreSQL, Python и Caddy, создаёт отдельного пользователя
приложения и локальную PostgreSQL, генерирует runtime-секреты на VM и включает
HTTPS-прокси. Секреты лежат в `/etc/tflow/app.env` с правами `0600`.
Данные PostgreSQL и `/var/lib/tflow` сохраняются между релизами.

## Установка проверенного релиза

Скачайте артефакты успешного job `package` нужного pipeline из GitLab и загрузите
архив и manifest в `/srv/tflow/incoming` на VM. Затем:

```sh
sudo python3 install-release.py /srv/tflow/incoming/manifest.json /srv/tflow/incoming/tflow-release.tar.gz
sudo systemctl status tflow caddy postgresql
```

Установщик сверяет SHA-256, проверяет пути архива, собирает отдельное окружение
Python, сохраняет резервную копию PostgreSQL в `/var/backups/tflow`, применяет
миграции и статику, переключает `/srv/tflow/current` и проверяет `/api/health`.
При неудачном запуске возвращает предыдущий код; резервная копия БД сохраняется.
Автоматически откатывать схему БД он не пытается.

Приложение работает от `tflow` через Gunicorn на `127.0.0.1:8000`.
Caddy обслуживает публичный HTTPS и продлевает сертификат.
Логи: `sudo journalctl -u tflow -u caddy`.
Полный Git-репозиторий размещается отдельно в `/srv/tflow/repository`.

## Вебинары на VM

Приложение и LiveKit запускаются отдельными службами. После успешной сборки
`master` используйте ручную задачу `provision-owned-video`: она устанавливает
LiveKit 1.13.11, сертификат и TURN, проверяет TLS, доступ API и медиапорты.
Совместимое задание `deploy_vm` сохраняет прежнее условие запуска, но вызывает
тот же установщик приложения; при `TFLOW_CONFIGURE_VIDEO=1` — ту же процедуру
настройки видео. Отдельная вторая видеослужба больше не создаётся.

Для приложения используется существующая задача `deploy-spirit-cu`
(доступ через ЦУ) или `deploy-spirit` при доступном публичном HTTPS.

Публичный адрес видео — `wss://tflow-video-162f2c.duckdns.org:8080`,
внутренний API — `http://127.0.0.1:7880`. Медиа использует TCP 8081
и UDP 8082, TURN TLS — TCP 8083. Доступность эфира нужно дополнительно
проверять двумя независимыми сессиями ведущего и зарегистрированного зрителя
из той сети, в которой будет работать мероприятие.

Для проверки состояния используются `systemctl status tflow-video caddy tflow`
и ручная read-only задача `spirit-readiness`. Исходящие сетевые ограничения VM
учтены выпуском сертификата и загрузкой проверенного бинарника в сети CI.



### Повторная настройка видеосервера

`provision-owned-video` сохраняет API-ключи в приватной конфигурации LiveKit на VM,
а ключ DNS-релея — в `/etc/tflow-video/dns.json`. При повторном запуске без
`TFLOW_VIDEO_KEY`, `TFLOW_VIDEO_SECRET`, `TFLOW_DNS_HOOK_SECRET` установщик
использует сохранённую конфигурацию VM. По закреплённому SSH она передаётся
в закрытый временный каталог CI для выпуска сертификата и проверки API;
значения не печатаются и не входят в артефакты. При первой
установке нужно передать все три значения; для смены API-ключей передаются
оба значения вместе. Ключ DNS-релея должен совпадать с production-переменной
`TFLOW_DNS_HOOK_SECRET` проекта Vercel `tflow`.




### Сертификаты при ограниченном исходящем доступе VM

`provision-owned-video` выпускает DNS-01 сертификат в изолированном каталоге CI
через подписанный релей `tflow-one.vercel.app`. Сертификат, приватный ключ и
проверенный по SHA-256 LiveKit передаются на VM по SSH с закреплённым ключом
хоста. Они не попадают в артефакты, исходники или вывод job. VM использует
сохранённые файлы без подключения к DNS-провайдеру, Vercel и GitHub.

Повторный запуск сохраняет действующий сертификат, если до его истечения
больше 30 дней, и повторно использует установленную версию LiveKit. Для
автоматического обновления используется pipeline schedule на `master` с
`TFLOW_MEDIA_RENEWAL=1`; он запускает только задачу настройки видео автоматически,
деплой приложения и операции управления VM при таком запуске не выполняются.




### Проверка реальной передачи медиа

После проверки HTTPS/API процедура запускает два независимых клиента
в отдельной технической комнате. Ведущий передаёт синтетический звук,
цветные видеокадры и сообщение; зритель должен получить все три потока.
Камера и микрофон не используются, техническая комната удаляется после теста.
SDK установлен в изолированном временном окружении CI с закреплёнными версиями.
Плановая проверка не перезапускает уже работающие службы, если сертификат
и бинарник ещё пригодны; при необходимости обновления применяется установщик.

### Диагностика входящего трафика без перезапуска сайта

`spirit-video-ingress` читает реальные правила `/sg` группы vm1, проверяет
версию приложения, состояние трёх служб, локальный доверенный TLS видео и
UDP-listener. Одинаковые проверки выполняются после операции. Секреты,
конфигурация комнат и пользовательские данные не выводятся.

Проверка CI также передаёт синтетические звук, видео и чат в отдельной
технической комнате. Ключи берутся через закреплённый SSH в приватный временный
каталог CI; установщик и обновление сертификата не вызываются.

По умолчанию сетевые правила только читаются. Явный `TFLOW_VIDEO_ALLOW_UDP=1` разрешает
единственное добавление: ingress UDP 8082 от `0.0.0.0/0`. Уже открытый порт
повторно не добавляется; TCP-правила должны существовать заранее. Шаблон
не применяется, существующие правила не удаляются, службы не перезапускаются.
Ответ 403 означает, что изменение должен сделать администратор инфраструктуры;
успешное состояние службы не выдаётся за доступность из внешнего браузера.

Для проверки из ветки `Sviat` предусмотрен отдельный API pipeline с
`TFLOW_VIDEO_NETWORK_CHECK=1`. Он выполняет обычные тесты и этот job, но
не выкладывает приложение: production-deploy разрешён только для push в
основную ветку GitLab. Так можно проверить сеть, сохранив текущий релиз.

### Диагностика входящих соединений

На личной ветке `gosha` можно создать API/web pipeline и вручную запустить
`spirit-ingress-diagnostics`. Задача читает маршруты, firewall и состояния
блокировок только своей VM, не перезапуская службы и не меняя правила.
Адреса клиентов и содержимое комментариев скрываются в выводе.

Если на VM уже есть `tcpdump`, параметр `TFLOW_VIDEO_CAPTURE_SECONDS=90`
добавляет ограниченное по времени наблюдение за SYN-заголовками порта 8080.
Возвращаются только счётчики, без адресов клиентов и содержимого пакетов.
По умолчанию захват выключен; новые пакеты на VM не устанавливаются.

Ручная задача `spirit-video-media-port` отдельно добавляет недостающее входящее
правило UDP 8082, используемое LiveKit для медиа. Она сохраняет остальные
правила и проверяет результат через API Spirit; повторный запуск не создаёт
дубликат. Это не устраняет таймауты подключения к публичному IP до попадания
пакетов на VM.
