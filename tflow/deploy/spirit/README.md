# ТФлоу в Spirit

Тенант: `hack-mmk-25`. Выделенная платформой VM: `vm1`, Ubuntu 24.04,
4 vCPU / 8 ГБ RAM / 50 ГБ диска. Квота команды — одна VM.
DNS: `hack-mmk-25-vm1-162f2c.vm.prodcontest.com`, IP: `158.160.209.13`.

CI в GitLab запускает TypeScript, frontend-тесты, сборку Vite и Django-тесты
с отдельной PostgreSQL 16. После успешных проверок job `package` сохраняет
`release/tflow-release.tar.gz` и `release/manifest.json` с SHA коммита и SHA-256 архива.
Этот архив содержит собранный frontend и Django, без локальных БД и секретов.
Выкладка запускается кнопкой `deploy-spirit` в pipeline ветки `master`;
push сам по себе не перезапускает VM.

## Выкладка из GitLab

После успешных тестов и `package` откройте pipeline `master` и запустите
`deploy-spirit`. Job использует существующий сервисный аккаунт Spirit,
получает текущие SSH-реквизиты только для vm1 и хранит их во временном каталоге
с правами 0700/0600. В логи и артефакты ключи не попадают. Отдельные
`DEPLOY_KEY`, `DEPLOY_HOST`, `DEPLOY_USER` не требуются.

Перед подключением проверяются SHA коммита, SHA-256 релиза, ID VM и SSH host key.
Job обновляет чистый Git checkout на VM только fast-forward, загружает точный
артефакт и запускает установщик. Локальные изменения на VM не перезаписываются.
Повторный запуск того же артефакта не повторяет установку, если manifest совпадает.

После установки проверяются все три службы, внутренний healthcheck, публичный
HTTPS, страница регистрации и отказ в выдаче QR без входа. При ошибке TLS
job завершается **ошибкой**, даже если установка кода на VM прошла.
Он оставлен необязательным ручным шагом, чтобы внешний сетевой сбой не блокировал
проверки кода и слияние. Готовность публикации проверяйте по успешному
`deploy-spirit`, а не только по общему статусу pipeline.

В GitLab создаётся environment `production` со ссылкой на требуемый домен Spirit.

## Первичная настройка

В интерфейсе Spirit откройте VM и скачайте SSH-ключ. Храните его вне репозитория
с правами `0600`. Пользователь SSH — `ubuntu`, у него доступен `sudo`.
Скопируйте этот каталог на выделенную VM и выполните:

```sh
sudo python3 bootstrap.py hack-mmk-25-vm1-162f2c.vm.prodcontest.com
```

Скрипт устанавливает PostgreSQL, Python и Caddy, создаёт отдельного пользователя
приложения и локальную PostgreSQL, генерирует runtime-секреты на VM и включает
HTTPS-прокси. Секреты лежат в `/etc/tflow/app.env` с правами `0600`.
Данные PostgreSQL и `/var/lib/tflow` сохраняются между релизами.

## Установка проверенного релиза

Скачайте артефакты успешного job `package` нужного pipeline из GitLab и загрузите
архив и manifest в `/srv/tflow/incoming` на VM. Затем:

```sh
sudo python3 install-release.py /srv/tflow/incoming/manifest.json /srv/tflow/incoming/tflow-release.tar.gz
sudo systemctl status tflow caddy postgresql
```

Установщик сверяет SHA-256, проверяет пути архива, собирает отдельное окружение
Python, сохраняет резервную копию PostgreSQL в `/var/backups/tflow`, применяет
миграции и статику, переключает `/srv/tflow/current` и проверяет `/api/health`.
При неудачном запуске возвращает предыдущий код; резервная копия БД сохраняется.
Автоматически откатывать схему БД он не пытается.

Приложение работает от `tflow` через Gunicorn на `127.0.0.1:8000`.
Caddy обслуживает публичный HTTPS и продлевает сертификат.
Логи: `sudo journalctl -u tflow -u caddy`.
Полный Git-репозиторий размещается отдельно в `/srv/tflow/repository`.

## Вебинары на VM

Сайт Django и LiveKit — разные службы. `npm run dev` запускает видеосервер только
локально; production-служба `tflow` не делает этого автоматически.

После установки текущего кода, поддерживающего `LIVEKIT_API_URL`, настройте видео:

```sh
sudo python3 configure-video.py \
  --hostname hack-mmk-25-vm1-162f2c.vm.prodcontest.com \
  --public-ip 158.160.209.13
# Команда выше показывает план. Для применения на VM:
sudo python3 configure-video.py \
  --hostname hack-mmk-25-vm1-162f2c.vm.prodcontest.com \
  --public-ip 158.160.209.13 --apply
```

Скрипт скачивает LiveKit 1.13.11 из официального GitHub release и проверяет SHA-256.
Создаёт отдельную службу `tflow-livekit`, сохраняет исходные настройки в
`/var/backups/tflow/video-*`, настраивает Caddy `/livekit/*` и добавляет в защищённый
`/etc/tflow/app.env` четыре параметра. Существующий внешний видеосервер он
автоматически не заменяет. Произвольный пользовательский Caddyfile требует
ручного объединения. База данных не изменяется.

```dotenv
LIVEKIT_URL=wss://hack-mmk-25-vm1-162f2c.vm.prodcontest.com/livekit
LIVEKIT_API_URL=http://127.0.0.1:7880
# Ключ и секрет создаёт скрипт; не публиковать их.
```

Браузер получает только публичный адрес. Django обращается к RoomService по
loopback, поэтому управление эфиром не зависит от маршрутизации VM к своему
внешнему IP. Административный порт 7880 слушает только loopback, а файлы с
секретами недоступны обычным пользователям. systemd передаёт YAML службе через
`LoadCredential`.

Для этого варианта нужны публичный HTTPS с действующим сертификатом, TCP 443
для сигнализации, **TCP 8001** и желательно **UDP 8002** для медиа. Проверьте
правила как в Spirit, так и в гостевом firewall. Скрипт не изменяет сетевую политику
Spirit и не отключает firewall. TCP fallback помогает при закрытом UDP, но для
ограничивающих корпоративных сетей может понадобиться отдельный TURN/TLS.
Только reverse proxy HTTP не обеспечивает доставку аудио/видео.

Проверка API с тем же окружением, что у приложения:

```sh
sudo systemd-run --quiet --wait --pipe --collect \
  --property=User=tflow --property=Group=tflow \
  --property=EnvironmentFile=/etc/tflow/app.env \
  --property=WorkingDirectory=/srv/tflow/current/tflow/backend \
  /srv/tflow/current/.venv/bin/python manage.py check_webinars
sudo systemctl status tflow-livekit tflow caddy
sudo journalctl -u tflow-livekit -u tflow -n 60 --no-pager
```

`check_webinars` проверяет настройки и авторизованный `ListRooms`, не создавая
комнат и не выводя ключи/список людей. Успех этой команды ещё не доказывает
доступность публичного WSS и медиапортов из браузера. Для итоговой проверки нужны
две независимые сессии ведущего и зарегистрированного участника, вход, чат,
аудиодорожка и выход/завершение.

Документация LiveKit: [порты](https://docs.livekit.io/transport/self-hosting/ports-firewall/),
[публичный адрес и TLS](https://docs.livekit.io/transport/self-hosting/deployment/).

## Деплой из GitLab

В `.gitlab-ci.yml` есть ручная задача `deploy_vm` после успешного `package`.
Она проверяет SHA коммита и SHA-256 артефакта, загружает ровно этот релиз на VM,
запускает существующий установщик с резервной копией БД и проверяет LiveKit API.
Задачи деплоя сериализуются `resource_group`, чтобы два релиза не переключали
`current` одновременно.

Нужны protected **File** variables проекта:

- `TFLOW_VM_SSH_KEY`: SSH-ключ пользователя ubuntu.
- `TFLOW_VM_KNOWN_HOSTS`: заранее проверенная запись ключа хоста VM в формате
  OpenSSH known_hosts. Получать/сверять fingerprint нужно по доверенному каналу,
  а не отключать проверку ключа сервера.

Для установки управляемой видеослужбы задайте `TFLOW_CONFIGURE_VIDEO=1`.
Для внешнего LiveKit оставьте `0` и настройте его адрес/ключи в `/etc/tflow/app.env`.
Не сохраняйте ключи в YAML, исходниках или выводе job. GitLab сам по себе
не устанавливает релиз только от наличия подключённой VM: задача должна иметь
рабочий сетевой маршрут и полномочия SSH. Успех GitLab-тестов/упаковки также
не означает, что задача `deploy_vm` запускалась или что WebRTC доступен снаружи.

### Повторная настройка видеосервера

`provision-owned-video` сохраняет API-ключи в приватной конфигурации LiveKit на VM,
а ключ DNS-релея — в `/etc/tflow-video/dns.json`. При повторном запуске без
`TFLOW_VIDEO_KEY`, `TFLOW_VIDEO_SECRET`, `TFLOW_DNS_HOOK_SECRET` установщик
использует эти файлы на самой VM: секреты не возвращаются в CI. При первой
установке нужно передать все три значения; для смены API-ключей передаются
оба значения вместе. Ключ DNS-релея должен совпадать с production-переменной
`TFLOW_DNS_HOOK_SECRET` проекта Vercel `tflow`.
