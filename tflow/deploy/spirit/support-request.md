# Недоступность публичного IP VM из внешних сетей

Просим проверить внешнюю маршрутизацию и фильтрацию публичного IP виртуальной
машины. Приложение работает внутри VM, но выпуск публичного TLS-сертификата
невозможен из-за таймаутов входящего соединения со стороны Let's Encrypt.

- Тенант: `hack-mmk-25`.
- Группа: `b9c06327-85dd-4ac8-adf6-3c5fcffb52e1`.
- VM `vm1`: `162f2c6f-c180-4eca-ad4c-9f23f18ce34e`.
- Публичный IP: `158.160.209.13`.
- FQDN: `hack-mmk-25-vm1-162f2c.vm.prodcontest.com`.

Проверка HTTP из Москвы возвращает `308 Permanent Redirect`, из Лос-Анджелеса —
`Connection timed out` к этому же IP. Результат независимой проверки:
https://check-host.net/check-report/54a20366kee5

На VM Caddy 2.11.7 слушает TCP 80/443. UFW неактивен, цепочки INPUT/OUTPUT
iptables — ACCEPT, перенаправления этих портов в Docker отсутствуют. В Spirit
успешно повторно применён шаблон Default: входящий TCP 22/80/443/8000–8100 от
0.0.0.0/0, исходящий трафик разрешён. Yandex metadata подтверждает привязку
публичного IP к интерфейсу VM `10.130.0.21`.

Проверки ACME HTTP-01 и TLS-ALPN-01 завершаются:

```text
158.160.209.13: Timeout during connect (likely firewall problem)
```

`/api/health` локально возвращает 200, службы Django, PostgreSQL и Caddy активны.
Просим устранить внешнюю фильтрацию/проблему маршрутизации либо предложить
замену публичного IP с сохранением VM и её диска. В интерфейсе редактирования
поле публичного IP недоступно; пересоздание предупреждает об удалении данных
корневого диска, поэтому его не выполняли.

Учётные данные, SSH-ключи и пароли для диагностики не требуются.
